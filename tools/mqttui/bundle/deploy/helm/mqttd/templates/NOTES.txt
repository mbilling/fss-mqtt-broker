mqttd {{ .Chart.AppVersion }} deployed as a {{ .Values.replicaCount }}-node StatefulSet
"{{ include "mqttd.fullname" . }}" in namespace "{{ .Release.Namespace }}".

Cluster formation (ADR 0016):
  - Pod {{ include "mqttd.fullname" . }}-0 is the gossip founder (no seeds); pods 1..N seed to it
    over the headless service "{{ include "mqttd.headlessName" . }}", and the mesh self-forms.
  - Each pod's node id is its stable pod name; each has its own PersistentVolume for the redb
    data dir, so a rescheduled pod recovers its durable state.

Check status:
  kubectl -n {{ .Release.Namespace }} rollout status statefulset/{{ include "mqttd.fullname" . }}
  kubectl -n {{ .Release.Namespace }} get pods -l app.kubernetes.io/instance={{ .Release.Name }}

Connect (from inside the cluster):
  Client service:   {{ include "mqttd.fullname" . }}.{{ .Release.Namespace }}.svc:{{ (index .Values.service.ports 0).port }}

{{- if not .Values.secrets.tls.secretName }}

WARNING: no TLS Secret is set (secrets.tls.secretName is empty). The config references
{{ .Values.secrets.tls.mountPath }}/tls.crt — set secrets.tls.secretName to a
kubernetes.io/tls Secret, or the TLS listener will fail to start. Provision TLS (e.g. with
cert-manager) before serving clients.

  First time? deploy/helm/mqttd/bootstrap.sh mints the gossip key, server TLS, per-node
  cluster-bus certificates and a starter ACL into your namespace and prints the exact
  `helm install --set` flags to wire them. Run it, then re-run helm with those flags.
{{- end }}
{{- if not .Values.secrets.peerTls.secretName }}

NOTE: the cluster bus is PLAINTEXT (secrets.peerTls.secretName is empty). Inter-node
traffic — every routed message and every session handoff — is readable and forgeable by
anything that can reach port 7001, and each broker logs this at startup as an INSECURE
mode. Fine on a trusted network; not fine otherwise.

  To turn it on you need ONE CERTIFICATE PER NODE, in a Secret holding ca.crt plus
  <pod>.crt / <pod>.key for each pod. A single shared certificate cannot work: the bus
  binds node identity to the certificate's Subject CN, so every link would be dropped.
  Each leaf needs CN = the pod name ({{ include "mqttd.fullname" . }}-<ordinal>), a SAN
  covering <pod>.{{ include "mqttd.headlessName" . }}.{{ .Release.Namespace }}.svc.cluster.local,
  BOTH serverAuth and clientAuth EKUs, and an ECDSA/Ed25519 key (never RSA — the same key
  signs gossip). bootstrap.sh mints exactly that; see the notes by `peerTls` in values.yaml.
{{- else }}

Cluster bus: mutually authenticated from Secret "{{ .Values.secrets.peerTls.secretName }}".
Each pod reads its OWN leaf ({{ .Values.secrets.peerTls.mountPath }}/$(POD_NAME).crt), because the
bus binds node identity to the certificate's Subject CN. That Secret must therefore carry
ca.crt plus <pod>.crt / <pod>.key for EVERY ordinal 0..{{ sub (int .Values.replicaCount) 1 }}
— a pod whose ordinal has no leaf fails its init container and says so. Expect "SWIM gossip
is SIGNED per-node" in each log; if you instead see "does not match its certificate Common
Name", a leaf's CN is not its pod name.
  Growing the cluster? Mint the new ordinals' leaves BEFORE raising replicaCount:
    REPLICAS=<n> ./deploy/helm/mqttd/bootstrap.sh
{{- if not .Values.secrets.gossipKey.secretName }}

WARNING: secrets.peerTls is set but secrets.gossipKey is EMPTY. The peer links are
mutually authenticated, but without MQTTD_SWIM_KEY_FILE the gossip plane runs
UNAUTHENTICATED (each broker logs "INSECURE: SWIM gossip is UNAUTHENTICATED") — anyone
who can reach UDP 7946 can inject membership claims. This pairing is almost never what
you want: set secrets.gossipKey.secretName (bootstrap.sh creates mqttd-gossip).
{{- end }}
{{- end }}
{{- if not .Values.secrets.acl.configMapName }}

WARNING: no ACL is set (secrets.acl.configMapName is empty). Topic authorization is then
NOT ENFORCED: every authenticated client may publish and subscribe anywhere. The broker
logs this at startup as an INSECURE mode. Provide a deny-by-default ACL ConfigMap before
serving real clients.

  (This warning exists because a missing TLS Secret fails loudly — the listener will not
   start — while a missing ACL fails QUIETLY, in the permissive direction. The one that
   fails open is the one worth warning about.)
{{- end }}

Before sizing this for production, read docs/SIZING.md in the chart's repository — it
states what each quota bounds, what nothing bounds yet, and the per-connection numbers
the defaults assume. The values.yaml quotas are a starting point, not a recommendation.
{{- if not .Values.clusterEstablished }}

NOTE: clusterEstablished is false, which is correct for a FIRST install — pod-0 founds the
cluster. Once the cluster is formed and healthy, set it to true and upgrade:

  helm upgrade {{ .Release.Name }} <chart> --set clusterEstablished=true --reuse-values

Leaving it false means a pod-0 that loses its volume will found a SECOND cluster beside the
live one instead of rejoining it (ADR 0054).
{{- end }}
{{- if .Values.bridge.enabled }}

BOUNDARY BRIDGE: the store-and-forward spool holds cross-zone message payloads in the clear
while a side is down. On a boundary host that is a plaintext copy of everything crossing the
boundary, so its volume MUST be encrypted at rest. Set bridge.persistence.storageClassName to
an ENCRYPTED StorageClass (e.g. AWS EBS encrypted: "true", GCP CMEK, Azure encryption-at-host);
an unset value uses the cluster default class, which is safe only if that default is encrypted.
This is the standard data-at-rest control — brokers do not encrypt their own spool either. See
docs/BRIDGE.md ("Encrypt the spool at rest").
{{- end }}

Safe operations:
  - Scale down (a lossless decommission drain, ADR 0043):
      kubectl -n {{ .Release.Namespace }} scale statefulset/{{ include "mqttd.fullname" . }} --replicas=<n>
  - Upgrade (one pod at a time, quorum-safe, ADR 0039):
      helm upgrade {{ .Release.Name }} <chart> ...
  - Validate a config change before rolling it out:
      mqttd --check-config --config <your file>   # or rely on the check-config init container
