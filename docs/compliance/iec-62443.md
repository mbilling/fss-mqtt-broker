# IEC 62443 mapping — secure development (4-1) and component requirements (4-2)

**Verified against `v1.0.8` (2026-08-26).** ADR 0067 T1: how this project's
practices map to IEC 62443-4-1's secure development lifecycle, and how the
broker's capabilities map to 62443-4-2's component requirements, with the
achievable security-level read stated per area. **No 62443 certificate is held
or implied**; this is the evidence a plant integrator's assessment starts from,
in the standard's own vocabulary. Rows cite the mechanism and where to check it.

## Part 4-1 — Secure product development lifecycle practices

| Practice | What the standard asks | This project's evidence |
|---|---|---|
| **SM** Security management | A defined, followed development process with security ownership | The ADR discipline (70 records, decisions with rationale and tasks), CI-gated delivery evidence (STATUS.md generated from per-task front-matter), one accountable maintainer — bus factor honestly stated in [THREAT-MODEL](../THREAT-MODEL.md) residuals |
| **SR** Security requirements | Security requirements specified and traced | Threat model rows name mechanism ↔ ADR ↔ enforcement site; the frozen-surface enumeration (ADR 0038 §D) is the must-touch trace for changes |
| **SD** Secure by design | Defense in depth, least privilege, attack-surface reduction as design acts | Deny-by-default at every layer, fail-closed refusal matrix, deliberate absences (no HTTP admin), effect-free refusals — each an ADR, not a habit |
| **SI** Secure implementation | Coding standards, no known-vulnerable constructs | Memory-safe Rust; clippy (all targets) gated; one crypto provider (ADR 0053); `cargo-deny`/`cargo-audit` on every PR |
| **SVV** Verification & validation | Security testing incl. abuse cases, fuzzing | Red-first/mutation-proven test discipline; continuous fuzzing (6 targets, nightly); chaos/partition/upgrade/soak harnesses; the acked-facts oracle; foreign-client conformance suites |
| **DM** Defect management | Vulnerabilities tracked, fixed, disclosed | [SECURITY.md](../../SECURITY.md) coordinated disclosure; GHSA + VEX per release; the review-panel method files defects as issues with two-exit discipline |
| **SUM** Update management | Secure, timely, verifiable updates | Signed reproducible releases with SBOM+SLSA; patch releases change no formats (ADR 0039); three supported lines ([SUPPORT.md](../../SUPPORT.md)); migrate-in-place contract (ADR 0058) |
| **SG** Security guidelines | Hardening and integration guidance for the operator | [HARDENING.md](../HARDENING.md) (34 checkable items), [SECURED-CLUSTER-TUTORIAL](../SECURED-CLUSTER-TUTORIAL.md), [OPERATIONS](../OPERATIONS.md), [AUDIT-SCHEMA](../AUDIT-SCHEMA.md) |

**Honest 4-1 gaps**: formal security-requirements *documents* per feature (ours
live inside ADRs, not a requirements register); independent third-party
verification (0065-T6, planned, funded audit); and the standard's expectation of
organizational role separation, which a solo-maintainer project cannot satisfy —
compensated, not cured, by the external review-panel method and public evidence.

## Part 4-2 — Component requirements by foundational requirement

Read: **SL-C** = the capability level a correctly-deployed mqttd can support.
Representative CRs per FR; a full CR-by-CR workbook is assessment-time work.

| FR | Area | Capability evidence | SL-C read |
|---|---|---|---|
| **FR1** Identification & authentication control | Argon2id passwords, mTLS (EKU + SAN-source discipline, CRL live), OIDC asymmetric-only, MQTT 5 enhanced auth (challenge/response), per-node cluster identity (CN-bound), keyed+signed+sequenced gossip postures | Human & software users uniquely identified/authenticated: **SL 2–3** territory; hardware-backed credentials and MFA are the deployment's (SL 4 items are out of component scope) |
| **FR2** Use control | Deny-by-default ACL (deny-wins, placeholder fail-closed), `connect` rules binding client-ids to identities, session-owner guard, live revocation sweeps (reload evicts) | Authorization enforcement on every use: **SL 2–3**; no per-operation dual approval (SL 4) |
| **FR3** System integrity | Schema-gated stores, epoch fencing, hash-chained audit with independent verifier, signed updates, backup sha-256 + refusal matrix, config validate-before-swap | **SL 2–3**; runtime code attestation is the platform's |
| **FR4** Data confidentiality | TLS 1.3 only by default (1.2 explicit opt-in), no plaintext listeners unless opted+announced; at-rest encryption delegated to platform, stated | In transit: **SL 2–3**. At rest: **SL 1** from the component (platform completes it) — stated, not hidden |
| **FR5** Restricted data flow | Topic-level segmentation via ACL, cluster plane on a dedicated mTLS CA (never the client CA), no cross-plane trust, bridge as an explicit boundary process (own identity, own failure domain) | **SL 2–3** |
| **FR6** Timely response to events | The audit trail: 16-kind vocabulary, SIEM export with boundary-alert invariants, seq-gap shed detection, `audit-verify.py`; metrics + drop counters per refusal class | **SL 2–3** |
| **FR7** Resource availability | Admission caps before TLS, penalty box, per-subscriber bounds, brownout watermarks (refuse growth, keep serving), quorum floor refusing unsafe writes, graceful degradation proven under kill/partition harnesses | **SL 2–3**; the memory mark is a watermark not a ceiling (recorded residual — the container limit completes it) |

**Honest 4-2 gaps**: no session-lock/inactivity-timeout beyond keep-alive
semantics (CR 2.5-class); password *policy* enforcement (complexity/aging) is
the credential-issuer's, not the broker's; wireless/portable-media CRs are not
applicable to a broker component; and every SL claim above is **SL-C**
(capability) — the achieved SL of a deployment is set by the operator following
the [hardening baseline](../HARDENING.md), which is written to be the bridge.

Corrections follow the repository rule: versioned, dated, re-stamped each
release (ADR 0067 T4).
