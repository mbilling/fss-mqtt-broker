    title: PVC retention defaults to Retain on scale-down (scaling to zero destroyed every volume, issue #97), and the chart path proves both split-brain mechanisms
    status: done
    date: 2026-08-07
    evidence: "Shipped in 44b2d84 (#99) and 9cdda43 (#103); recorded 2026-08-07 in a delivery-record audit. kubectl scale --replicas=0 on a durable cluster SILENTLY ERASED ALL DURABLE STATE — every PVC deleted, and the next scale-up formed a brand-new empty cluster with a new identity (verified on kind: 95a206b9 -> b7afa164, no warning anywhere). The chart shipped whenScaled: Delete with a sound justification — a scale-down drains first, so the departing volume holds only superseded state and deleting it also closes the stale-rejoin trap — but it carries an UNSTATED PRECONDITION: a survivor must remain to receive the drain. Kubernetes applies the policy uniformly and has no notion of shrink-to-a-floor versus shrink-to-nothing, so at zero the deletion stops reclaiming migrated data and starts erasing the only copy. Both policies now default to Retain: an orphaned volume after a shrink is visible and reversible, silent total loss is not. Operators who shrink often and never scale to zero can set Delete back; the stale-rejoin trap it closed is now theirs to close deliberately, documented in OPERATIONS.md alongside reclaiming orphans, reusing an ordinal, and restarting a fleet safely (rolling restart, never scale-to-zero). ADR amended. ALSO: kind-smoke now proves both split-brain mechanisms on the CHART path — self-quarantine (0054-T5) and the founder guard (0055-T9) — because a chart-only deployment has no controller to compensate and was the path with no end-to-end proof. Ordering there is load-bearing and cost three runs to learn: a StatefulSet rolls highest-ordinal-first, so with pod-0 already NotReady the roll never reaches ordinal 0 and the controller recreates it at the OLD revision; and after self-quarantining, pod-0's volume holds the divergent identity it minted, so it must be wiped again — which is exactly the recovery OPERATIONS.md prescribes."

The named volume also removes an inferred ./secrets bind-mount trap: bootstrap.sh makes that directory 0700 owned by the invoking user, which uid 65532 cannot traverse on a native-Linux docker host, invisible under Docker Desktop's uid mapping. Plaintext returns only through deploy/compose/compose.plaintext.yaml (`docker compose -f compose.yaml -f compose.plaintext.yaml up -d`), loopback-only, deliberately NOT named compose.override.yaml because Compose loads that name automatically and a stray copy would downgrade a cluster with nothing in the output saying so. systemd: mqttd.env.example flips the same way — MQTTD_TLS_BIND/CERT/KEY and the MQTTD_PEER_TLS trio uncommented with the four peer-certificate rules stated at the point of use, MQTTD_PLAINTEXT_BIND commented and labelled INSECURE, so an unedited install fails closed instead of serving cleartext, with `cannot read MQTTD_PEER_TLS_CA (/etc/mqttd/tls/peer-ca.pem): No such file or directory (os error 2)`. The PKI itself is a SCRIPT, deploy/systemd/gen-certs.sh, not openssl commands in a comment: the comment version could not run ($PEER_HOST was defined nowhere, so the CSR got an empty subject and openssl hard-failed on `subjectAltName=DNS:`) and nothing executed it, which is the same defect class as the one this task exists to fix. The script mints ONE CA for the cluster with that contract stated (a per-host CA gives every node a different trust root: no peer handshake and no gossip verification succeeds, so all three brokers start, log SIGNED per-node, and never pass the readiness floor with nothing naming the cause), mints per-node leaves with CN = node id and the advertise host in the SAN, uses ECDSA P-256, takes the node id and advertise host as real arguments, keeps the CA PRIVATE key on the admin machine and out of every per-node directory, and prints per-file `install` commands instead of a `chmod /etc/mqttd/tls/*.key` glob — that glob handed the cluster CA key to the broker's own service account, group-readable, on every host, which is 'insecure while the project's own words say secure' relocated from wire encryption to key custody. New scripts/compose-smoke.sh brings the SHIPPED compose file up in real containers on the nightly image lane — three healthy brokers, a TLS publish on node 3 reaching a TLS subscriber on node 1, the no-cafile and wrong-password refusals, no INSECURE in any container log, three signed-gossip lines, no published 1883, the overlay restoring plaintext AND logging INSECURE for it, and the missing-secrets case failing with a message that names ./bootstrap.sh — which also makes compose.yaml's long-standing 'tested by scripts/compose-smoke.sh' comment true rather than a comment naming a script that never existed. REJECTED ALTERNATIVE: the issue's exit (2) — delete 'secure by default' for compose, move the plaintext warning into the main README, and stop host-publishing 1883. It is cheaper and was refused because it leaves the default insecure: the artifact a reader copies would still be plaintext, and the only thing changed would be whose fault it is. No blocker for exit (1) existed — the one-shot cert pattern already ships twice in-repo (demo/quic/gen-certs.sh + demo/docker-compose.yml, deploy/helm/mqttd/bootstrap.sh) and the broker fails closed on every relevant path, so removing MQTTD_PLAINTEXT_BIND removes the fallback structurally rather than by a runtime check. One constraint was documented nowhere before this and cost a red run to find: the cluster-bus key is ALSO the per-node gossip signing key, and that signer accepts only PKCS#8 ECDSA P-256/P-384 or Ed25519 — so the RSA recipe every other bootstrap script in the repo uses yields a working TLS handshake followed by 'unsupported or unparseable gossip signing key' at startup. init.sh and the systemd env file both mint P-256 and both say why, at the point of use. VERIFIED LOCALLY on Docker Desktop (arm64) with an image built from the working tree, since per-PR CI never brings containers up: three brokers healthy ~10s after `up -d`; the README's mosquitto_sub/mosquitto_pub lines work verbatim (cross-node, node 3 -> node 1); `openssl s_client` reports TLSv1.3, subject CN=mqttd-1, ecdsa_secp256r1_sha256, verify return 0; `docker compose logs | grep -i insecure` empty and `grep -c 'SIGNED per-node'` = 3; a cleartext client on 8883 gets 'Protocol error'; `mqttd --probe /readyz` via `compose exec` returns 200; deleting the peer-TLS material with MQTTD_SWIM_SIGNED=require is a hard startup error, as is MQTTD_TLS_BIND without a cert; and the documented add-a-user flow behaves exactly as written, including that HUP alone is a no-op until `up -d init` restages. Fixed in the BINARY rather than by requoting: TLS material is now checked for readability with its variable's name attached before it reaches rustls (crates/mqttd/src/main.rs::tls_path_readable, covering MQTTD_TLS_CERT/KEY/CLIENT_CA/CRL and the MQTTD_PEER_TLS trio), and the cluster-identity write that produced the bare errno now names its file (crates/mqtt-cluster/src/cluster_identity.rs). The documented symptom is now what the binary prints, and the operator gets the setting to fix rather than a filename or an errno. Residual: per-PR CI still does not bring containers up — the real bring-up rides the nightly image lane, which is also the only native-Linux docker host in CI and therefore the only place the uid-65532 readability of the staged secrets is exercised. Also out of scope and worth a separate issue, found while getting this green: deploy/helm/mqttd/bootstrap.sh mints ONE shared peer leaf with CN=$RELEASE-node and no SANs, which cannot satisfy the peer CN binding for pods mqttd-0/1/2, AND mints it as RSA — the cluster-bus key doubles as the per-node gossip SIGNING key, which accepts only PKCS#8 ECDSA P-256/P-384 or Ed25519, so an operator who wires secrets.peerTls plus secrets.gossipKey from that script gets a working TLS handshake followed by a hard startup failure ('unsupported or unparseable gossip signing key'). Nothing catches it because values.yaml leaves both secretNames empty by default and scripts/k8s/kind-smoke.sh never wires secrets.peerTls.     notes: "The upgrade path is the one genuine regression and it is documented rather than coded around: deploy/compose/README.md gains an 'Upgrading an existing plaintext cluster' section with exactly ONE route — `down` then `up`; the volumes hold the durable state, so that is downtime, not data loss. An earlier draft of this record and of that section offered a second 'no outage, two rolls' route (MQTTD_SWIM_SIGNED=off for one roll) and justified it as 'signed gossip has no mixed mode'. That was wrong and is corrected here rather than quietly edited, because it is the kind of promise an operator plans a maintenance window around: the PEER BUS has no mixed mode either — a node with MQTTD_PEER_TLS_* starts a TLS peer acceptor and only that one, no sniffing and no fallback (crates/mqttd/src/peer.rs::serve_listener takes the plaintext branch only when its TLS context is None) — so a rolled node forms NO bus link with an un-rolled one whatever MQTTD_SWIM_SIGNED says. Setting it off keeps the gossip half whole and relocates the split onto the peer bus, where the minority half loses lease_group_ready and drops out of rotation while its listener still accepts clients, so QoS 1 durable publishes to it hang or fail; and roll 1 removes the 1883 the existing cluster's clients are on either way. The variable stays interpolated for the narrower job it can honestly do: choosing the shared-key gossip posture as one .env line rather than an edit to the shipped compose.yaml. Second cost: a second image is pulled on first `up`, so an air-gapped host now breaks at bring-up rather than at build — MQTTD_CERTGEN_IMAGE points at a mirror, and the demo's 'alpine + apk add openssl' shape was deliberately not copied because it needs network on every up. That image is PINNED, alpine/openssl:3.5.7, the way this repo pins every other third-party image (busybox:1.36 in demo/docker-compose.yml and bench/, initImage 1.36 in deploy/helm/mqttd/values.yaml); it shipped as a floating :latest at first, which meant the cluster's trust root was minted by whatever Docker Hub served that day and put an unauthenticated, unpinned pull in the nightly compose lane. The resolved digest is recorded in compose.yaml for anyone who wants to pin harder, and MQTTD_CERTGEN_IMAGE is an override, not the default. Third: `docker compose down -v` now destroys the CA too, so clients must re-trust after a wipe, and adding a user becomes append + `up -d init` + HUP because the brokers read a staged copy. Fourth, a new second edit point when the compose cluster is resized: the init service's MQTTD_NODES list decides how many leaves are minted, so a service block copied without touching it gets a node with no certificate. It fails closed (`cannot read MQTTD_PEER_TLS_CERT (...)`) but says nothing about MQTTD_NODES, so both the variable and deploy/compose/README.md now carry an 'Adding a node' procedure naming both edits."
