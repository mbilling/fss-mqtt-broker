  - id: 0047-T8
    title: PVC retention defaults to Retain on scale-down (scaling to zero destroyed every volume, issue #97), and the chart path proves both split-brain mechanisms
    status: done
    date: 2026-08-07
    evidence: "Shipped in 44b2d84 (#99) and 9cdda43 (#103); recorded 2026-08-07 in a delivery-record audit. kubectl scale --replicas=0 on a durable cluster SILENTLY ERASED ALL DURABLE STATE — every PVC deleted, and the next scale-up formed a brand-new empty cluster with a new identity (verified on kind: 95a206b9 -> b7afa164, no warning anywhere). The chart shipped whenScaled: Delete with a sound justification — a scale-down drains first, so the departing volume holds only superseded state and deleting it also closes the stale-rejoin trap — but it carries an UNSTATED PRECONDITION: a survivor must remain to receive the drain. Kubernetes applies the policy uniformly and has no notion of shrink-to-a-floor versus shrink-to-nothing, so at zero the deletion stops reclaiming migrated data and starts erasing the only copy. Both policies now default to Retain: an orphaned volume after a shrink is visible and reversible, silent total loss is not. Operators who shrink often and never scale to zero can set Delete back; the stale-rejoin trap it closed is now theirs to close deliberately, documented in OPERATIONS.md alongside reclaiming orphans, reusing an ordinal, and restarting a fleet safely (rolling restart, never scale-to-zero). ADR amended. ALSO: kind-smoke now proves both split-brain mechanisms on the CHART path — self-quarantine (0054-T5) and the founder guard (0055-T9) — because a chart-only deployment has no controller to compensate and was the path with no end-to-end proof. Ordering there is load-bearing and cost three runs to learn: a StatefulSet rolls highest-ordinal-first, so with pod-0 already NotReady the roll never reaches ordinal 0 and the controller recreates it at the OLD revision; and after self-quarantining, pod-0's volume holds the divergent identity it minted, so it must be wiped again — which is exactly the recovery OPERATIONS.md prescribes."

    status: done
    date: 2026-08-13
    evidence: "The mint shipped ONE leaf for the whole cluster — `CN=<release>-node`, no SANs, RSA 2048 — created Secret `mqttd-peer-tls` from it, and printed `--set secrets.peerTls.secretName=mqttd-peer-tls` as the way to turn the mutually-authenticated bus on. Three independent RUNTIME failures: the bus binds node identity to the Subject CN (crates/mqttd/src/peer.rs, and the same CN against the gossip sender in crates/mqtt-cluster/src/swim_driver.rs), so every pod claiming its own id under a shared CN has EVERY link dropped after a successful handshake; name verification uses SANs ONLY (crates/mqtt-net/src/tls.rs::server_name derives the dialer's ServerName from the peer's advertise host), so a leaf with none can never verify — CN and SAN are separate requirements and satisfying one says nothing about the other; and the peer key IS the per-node gossip signing key, which accepts only ECDSA P-256/P-384 or Ed25519 PKCS#8 (crates/mqtt-auth/src/signed_gossip.rs), so RSA yields a working handshake and then a hard startup error — and signed gossip ARMS ITSELF once peer TLS and a gossip key are both present (crates/mqttd/src/main.rs), so that leg is not opt-in. A fourth defect made the first three invisible and was the actual payload: the chart MOUNTED the Secret and referenced nothing in it, so the shipped instructions produced a mounted secret, a plaintext peer bus, and an `INSECURE: starting PLAINTEXT peer listener` line nobody was told to look for. NOW: one CA plus ONE LEAF PER ORDINAL (CN = pod name, SAN = that pod's `<pod>.<headless>.<ns>.svc.cluster.local` advertise host, both EKUs, ECDSA P-256 PKCS#8), keyed in the Secret by pod name; the chart DERIVES `MQTTD_PEER_TLS_{CA,CERT,KEY}` — each pod's own leaf via Kubernetes' dependent-env `$(POD_NAME)` expansion, which is what makes a per-node CN possible at all (a StatefulSet pod template cannot select a Secret per ordinal, but every pod can select a KEY inside one) — and `MQTTD_SWIM_KEY_FILE`, so mounted-but-unread is no longer expressible. The CA private key never enters the cluster. The mint VERIFIES ITSELF: CA:TRUE plus self-verification for the CA, and CN, SANs, both EKUs, CA:FALSE, named-curve P-256, ecdsa-with-SHA256 and a successful `openssl verify` for every leaf — failures accumulate so one run reports all of them, and material is staged and installed only after it passes. REUSE re-verifies what is on disk rather than stat-ing it, so a mint this script rejected is never blessed by a later run (proven: a planted RSA leaf, a planted shared-CN leaf, a non-CA `cluster-ca.pem` and a namespace change that invalidates the SANs are each refused with the rule cited and a remedy). Written to the LibreSSL-and-OpenSSL-3 intersection (`ecparam -param_enc named_curve` + `pkcs8 -topk8`, extensions through -extfile, an explicit -sha256) because it runs on the operator's workstation rather than in a pinned image, and VERIFIED ON BOTH: LibreSSL 3.3.6 (/usr/bin/openssl on macOS) and OpenSSL 3.6.2 each produced conforming material, CROSS-CHECKED so LibreSSL's output verifies under OpenSSL 3 (named-curve keys, X509v3 extensions present, no explicit ECC parameters, SHA-256 signatures) rather than only under the implementation that produced it. Scale-up has an answer: `REPLICAS=<n> ./bootstrap.sh` keeps and re-verifies the CA, existing leaves and gossip key and mints only what is missing (3→5 verified), and a pod whose ordinal has no leaf fails its INIT CONTAINER with a message naming that command instead of crash-looping on an unreadable path. GATES: kind-smoke now runs with the bus ON, minting through the shipped script rather than restating it, and asserts `mtls=true`, signed per-node gossip and the ABSENCE of CN-binding drops on every pod — verified locally end-to-end on kind, where the 3-node cluster formed over per-node mTLS, round-tripped a retained message, drained on scale-down and survived a quorum-safe roll; new `scripts/k8s/peer-tls-check.sh` (PR tier, no cluster) checks each leaf's CN against the pod names `helm template` renders and its SAN against the advertise host the chart's OWN init script computes — both read out of the artifacts, never restated — that the render consumes what it mounts (per-pod paths, POD_NAME ordered before the entries referencing it, and the default render still carrying none of it), that a real broker boots on a minted leaf with an mTLS peer listener and signed gossip, and, as a NEGATIVE CONTROL, that the original certificate is refused by both the mint's verifier (citing rules 1, 2 and 4) and the broker at startup; render-parity gained a third pass with the bus ON, so the operator path — which had the same mounted-but-unread gap, now mirrored in render.rs — cannot drift from the chart. Docs corrected at every point of use: values.yaml (the four rules, the scaling order, the residual, the cert-manager path), NOTES.txt (a real peer-bus warning plus a bus-on branch stating the per-ordinal requirement and the CN-mismatch symptom), bootstrap.sh's header, docs/OPERATIONS.md (a cluster-bus certificates section and the mint-before-you-grow order), docs/TROUBLESHOOTING.md (the never-ready-with-CN-mismatch symptom), docs/mqttd.example.toml, README.md, deploy/README.md, and the operator CRD schema (regenerated). Residual: on this starter path ONE Secret holds every node's key and Kubernetes hands a pod the whole Secret, so every broker pod can read every other node's peer key — the CN binding stops an outsider, not a compromised pod. Per-pod key isolation needs a per-pod issuer (cert-manager csi-driver, documented as the production path); a single cert-manager Certificate listing every pod's DNS name does NOT work here, because it has one CN and rule 1 is per-pod — that is the RabbitMQ inter-node shape this script was evidently copied from, which works there only because Erlang distribution does not bind node identity to the CN. Not verified on this host: section 6 of peer-tls-check.sh (two nodes linking over loopback) needs a writable /etc/hosts and SKIPS LOUDLY without one; it runs in CI, and the kind lane covers the same ground with real per-pod DNS."
    notes: "The fix is in two halves, and the structural half matters more than the certificates. Minting per-node leaves correctly still leaves the trap that produced this defect — an operator can mount a peer-bus Secret nothing reads — so the chart now derives the paths from the secret names, making announced-implies-consumed a property of the template rather than of the documentation. The verification discipline is the other half: nothing is printed that was not read back out of the file, because the previous script's failure mode was a confident banner for a certificate that could not work."

## Changelog

- **2026-08-10** — **T9 done: you can deploy this without Kubernetes.** The ADR was
  Kubernetes-only and OPERATIONS.md carried bare-metal prose with no artifact behind it,
  which every outside reviewer read as Kubernetes-or-nothing. `deploy/compose/` and
  `deploy/systemd/` now ship, secure by default, with `deploy/README.md` choosing between
  the four packagings. Enabled by `mqttd --probe`: Compose, Podman and systemd express
  health as a *command*, the image is distroless, and the only thing available to run was
  `--check-config` — which passes no matter what the broker is doing. A health check that
  cannot fail is worse than none. Tested by booting three real nodes from the SHIPPED env
  file (parsed, not restated) and asserting the security posture, cross-node routing, an
  acked QoS 1 message surviving `SIGKILL` of the node that accepted it, and a minority
  node reporting live-but-not-ready.
- **2026-07-17** — ADR 0047 drafted. Adoption enabler: "runs on Kubernetes" must preserve
  the durability/safe-shrink/safe-upgrade guarantees (ADR 0018/0043/0039) rather than lose
  them to misconfiguration (ephemeral storage, crash-on-scale, quorum-breaking rollouts).
  Priority **P1**.
- **2026-07-17** — Alternatives sharpened: added "N single-replica Deployments, each with its
  own PVC" (the *manual StatefulSet*) as a named, fairly-argued rejected option — it gets
  per-node durable storage right but rebuilds ordered rollout and template PVC provisioning by
  hand and walks into the `ReadWriteOnce` Multi-Attach rollout trap. Decision unchanged: keep
  the StatefulSet.
- **2026-07-19** — **T1–T4 done; T5 in-progress.** The Helm chart (`deploy/helm/mqttd`) ships: a
  StatefulSet with a per-pod `volumeClaimTemplate` (durable state survives reschedule), a
  `render-config` init container that solves per-pod identity for the *distroless* image (no shell)
  by writing node id = pod name and seeds = `[]` for the founder pod-0 / the pod-0 seed for the
  rest, a `check-config` init container that fails a bad config before it serves, `/readyz`+`/livez`
  probes, client + headless Services, a PDB (`maxUnavailable: 1`), and one-at-a-time RollingUpdate.
  The safe scale-down needed a broker primitive the ADR under-specified: `mqttd --decommission`
  (sends SIGUSR1 to the running broker — PID 1 — and blocks until it drains + exits), wired into the
  chart's `preStop`; unit+integration tested. The chart is validated offline in a new CI `helm` job
  (lint + template + kubeconform) and the rendered configs pass `--check-config`. Remaining (T5): the
  live kind/k3d runtime smoke (stand up → scale → roll, asserting no acked loss), which needs the
  image + a cluster and lands in the nightly tier — so the ADR stays Proposed until it is green.
