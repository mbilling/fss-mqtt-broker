  - id: 0062-T11
    title: "An export never overwrites another export, and the promise its own comment made is now true"
    status: done
    date: 2026-08-15
    evidence: "CI FOUND THIS ON MAIN, as a flake: `the_cluster_id_is_read_fresh_for_every_export_not_snapshotted_at_startup` failed with `two runs, two files: [ONE file]`. The cause was not the test. The export name carries milliseconds and its own comment claimed that made two exports two files rather than `one silently overwriting the other` - but `std::fs::rename` REPLACES, so two exports of one node that started inside the SAME millisecond left one file: the older generation destroyed, with no error, no log line and no metric. Milliseconds made it rare, not impossible, and a CI runner over an in-memory store is fast enough to hit it. THE FIX WAITS FOR THE CLOCK rather than nudging the name: bumping only the filename would leave both headers carrying the same created_unix_ms, and select_generations REFUSES a directory holding two exports of one node with equal timestamps (`which one is newer is not decidable`) - trading a silent loss for a directory nothing can be restored from. Leaving the occupied millisecond makes the name AND the recorded moment genuinely distinct, bounded by NAME_WAIT_MAX_MS=1000 and then refused loudly. Plus a second, independent guard: the rename REFUSES if the name was claimed during the scan, naming both paths, leaving the .partial as this run evidence for the next run clean_stale_partials. TESTS, both mutation-proven INDEPENDENTLY because the two mechanisms mask each other: an_export_whose_name_is_taken_leaves_the_existing_file_intact occupies a 200ms BAND of names so the collision is certain on any machine (removing the name choice -> RED with the guard refusal quoted), and an_export_refuses_rather_than_replace_a_name_claimed_during_its_scan drives the residual race through a RetainedSource that claims the band WHILE it is read - the one point between name choice and rename a test can reach (removing the guard -> RED). A third, an_export_never_takes_a_name_another_export_already_owns, pins the naming rule where its input can be fixed. Deliberately NOT shipped: a `run it twice and count the files` test, which passes with the fix removed on a slower machine - that is exactly how this reached main."
    notes: "The flaky-looking failure was a real data-loss defect, and the test was right. Recorded because the shape recurs: a comment that states a guarantee (`must be two files, not one silently overwriting the other`) sitting above code that does not enforce it, where the enforcement is a property of the CLOCK rather than of anything in the function."

## Why this shape

Issue #249's two acceptable exits were "ship an online export + import with a documented
RPO/RTO" or "say explicitly that online backup is out of scope for 1.0". This delivery
takes the **first** exit for the data plane (sessions and retained state) and the
**second**, in writing, for everything the data plane cannot honestly carry — lease/Raft
state, cluster identity, a cluster-wide instant, incremental backups, and the bridge
spool. Both halves are in OPERATIONS, in that order, because an operator who reads only
the first half must still learn what they are not covered for.

## The load-bearing test

`crates/mqttd/tests/backup_restore.rs::a_live_cluster_export_restores_sessions_retained_and_acked_facts`
is the acceptance criterion, over spawned production binaries rather than a unit fixture:
export from a LIVE cluster while clients are connected, restore into a FRESH one, and
verify through the client protocol that `session_present`, every acked payload, the
retained value with its v5 properties, and the acknowledged QoS-2 flow all survive. It
also proves the #242 hazard is absent — a node restarts over its own data dir immediately
after an export.

## Review round 3 (2026-08-15, before commit)

Round 2's remediation was right about everything it fixed, and one of its fixes was DEFEATED
BY ORDERING — which is the finding worth keeping. The mixed-cluster refusal was implemented
correctly and ran AFTER `select_generations`, which reduces a directory to one file per NODE
ID. So two clusters that name their nodes identically (staging beside prod, or a rebuilt
cluster — the `mqttd-0/1/2` shape) present as several generations of one node, the loser is
discarded in silence, and the refusal never sees a second cluster id. Both round-2 verifiers
proved it independently on real unrelated clusters: the wrong cluster's sessions and retained
values were imported with no error. **A refusal that the step before it has already hidden the
evidence from is not a refusal.** The check now runs over EVERY discovered file, before
selection; the test that missed it used two DIFFERENT node ids (so both files survived
selection and the refusal fired) and now carries the same-node-id case. Mutation-proven —
moving the check back after selection reds it with a plan importing the wrong cluster.

Also fixed from that round:

- **The composed set's SKEW was neither bounded nor mentioned.** A cluster backup is one export
  per node and those were taken at different moments, so the set is only as fresh as its OLDEST
  member — a node whose export is a day stale contributes a day-old view, resurrecting deleted
  sessions and re-queueing drained messages. The span is now measured, warned at restore time
  with both endpoints named, and kept in the stamp, because the log line will not survive the
  incident.
- **The `restored-from` stamp was not crash-safe.** It is the only thing that lets a restored
  node reboot, and it was written with a bare `fs::write` while the data it licenses was fsynced
  by redb — so a power loss in the page-cache window left a complete restore with no stamp, and
  a next boot whose printed remedy is to delete the data just recovered. Now
  write-fsync-rename plus a directory fsync.
- **An unreadable SUPERSEDED generation failed the whole restore**, contradicting the code's own
  claim that discarding a generation costs no parse. Now skipped loudly, with the coverage check
  as the backstop if it was a node's only export — while a file that PARSES but declares a newer
  format is still refused loudly (ADR 0058). The two failure kinds are separate functions now,
  because conflating them is exactly what made the first attempt at this fix break the
  format-refusal test.
- Smaller: the one log line naming files labelled the IGNORED generations as `files=`;
  `mqttd --backup` inherited `--decommission`'s one-hour timeout while a failed export writes no
  `.ndjson`, so it blocked 55 minutes past a failure the broker recorded in milliseconds (now
  300 s, `--timeout` still overrides); `backup_duration_ms`'s HELP still conflated the run's wall
  clock with the consistency window after the docs had been corrected; and ADR 0062 claimed the
  stamp reports superseded generations by count, which it never did — it now points at `skew_ms`,
  the number that actually bounds staleness.
