    title: "`SessionStore` outbound in-flight table: record / advance / clear / read, replicated with the session"
    status: done
    date: 2026-08-10
    evidence: "crates/mqtt-storage: record_outbound/advance_outbound/clear_outbound/outbound on SessionStore, with the write-before-send ordering contract in the trait docs (same as #124's) and the QoS-1 exclusion stated where someone would look for it. ReplicatedSessionStore keeps the window in the m/{client} metadata snapshot beside the inbound window — equally small and low-churn, bounded by receive-maximum — encoded as a backward-compatible tail after the ADR 0031 owner field. MemorySessionStore and both test FlakyStores implement it; the flaky ones gate the writes behind the same fault seam as enqueue, so T2's fail-closed test has its lever. 62 storage tests green."
    notes: "Two tests carry the load: a failover replica sharing only the log sees id, offset AND PHASE (asserted explicitly, because the phase is what decides PUBLISH+DUP versus PUBREL on resume — resuming in the wrong phase either re-sends a message the subscriber holds or releases one it never got); and a pre-0057 metadata record decodes with an empty outbound window rather than an error. The old record is constructed by BYTE-TRUNCATING a modern one at the owner field's end, not by trusting the encoder to remember what the old format was."
  - id: 0057-T2
    title: "Hub wiring: write at allocation and PUBREC, clear at PUBCOMP, fail closed with the ack withheld when the write fails"
    status: done
    date: 2026-08-10
    evidence: "crates/mqttd/src/hub.rs — send_qos_publish records the id durably BEFORE the PUBLISH reaches the wire (QoS 2 with a durable offset only); pub_rec advances the record durably BEFORE the PUBREL goes out; pub_comp clears it. Each failure has its own semantics and its own retry story: a failed record withholds the PUBLISH and requeues at the backlog FRONT (the message is already durable from #124, so nothing is lost — only deferred, in order); a failed advance withholds the PUBREL, and the subscriber's own PUBREC re-send is the retry; a failed clear is logged and tolerated, because the worst a leftover entry does is one spurious PUBREL on restore, which the subscriber answers with PUBCOMP (MQTT-4.3.3) — and THAT retries the clear. Four hub unit tests; 186 total green."
    notes: "Writing the deferral test exposed an ordering hole in the first design: pre-0057, backlog-non-empty implied quota-full (acks drain before the loop processes another publish), so fresh traffic could never overtake the backlog. A deferred delivery broke that invariant, and a new publish would have jumped ahead of it — per-client ordering is part of the contract. The deliver gate now also diverts on backlog-non-empty, and a publish that finds quota free retries the drain, making traffic the deferred delivery's retry clock instead of the next reconnect. The FlakyStore fault seam gained a SEPARATE fail_outbound lever, because the enqueue lever fires first and would mask the very path these tests exercise."
  - id: 0057-T3

    evidence: "Reconciliation (found by the 2026-08-20 delivery validation): the substance shipped long since and later records already leaned on it — the storage API (record_outbound / advance_outbound / reserve_packet_ids, mqtt-storage/src/lib.rs) rebuilds pending outbound state on restore, ADR 0062's restore path replays it (record_outbound + advance_outbound for pubrec_seen, reserve_packet_ids last for the id high-water, per 0062-T4's evidence), and 0057-T4's own notes describe its SIGKILL proof as 'the out-of-process proof the in-process T3 tests approximated' — T4 (done) is the acceptance evidence for T3's mechanism: PUBREL under the known id after PUBREC, PUBLISH+DUP under the original id before it, allocator seeded past restored ids. This row simply never got flipped when the work landed."
  - id: 0057-T4

    status: done

    evidence: "crates/mqttd/tests/inflight_durability.rs — the #130 acceptance criterion VERBATIM, against the real binary: subscriber PUBRECs, broker SIGKILLed (no flush, no goodbye), restart on the same data dir, and the resumed session receives PUBREL for the id it already knows — with the failure arms spelling out why a fresh-id PUBLISH is the defect. The companion covers the pre-PUBREC phase: PUBLISH re-sent with DUP under the ORIGINAL id, exactly one copy, and the handshake completes under it.     notes: "This is the out-of-process proof the in-process T3 tests approximated: a real SIGKILL, a real redb recovery, a real session resume."
  - id: 0057-T5
    title: "Measure the QoS 2 delta in the bench lane; record it; revisit the on-by-default decision if indefensible"
    status: done
    date: 2026-08-11
    evidence: "MEASURED (dev-grade: one machine, arm64 macOS, mosquitto clients, 500x256B end-to-end, persistent subscriber, MQTTD_DURABLE_SESSIONS=1, 3 runs per lane, baseline = dd3df27 pre-hub-wiring vs main): QoS 2 wall time roughly DOUBLES — 12.4/14.3/17.1s baseline vs 26.8/28.5/29.3s current, ~40 -> ~19 msg/s — consistent with the mechanism (up to three additional fsync-bound metadata writes per delivery: record at send, advance at PUBREC, clear at PUBCOMP). The QoS 1 CONTROL lane shows no delta (6.4/8.1/10.4 vs 5.9/7.5/9.0 — current marginally faster, i.e. noise), which is the check on the check: the QoS 1 exclusion held, and the measurement itself is sound. VERDICT: defensible; on-by-default stands. The cost lands only on the flow that asked for exactly-once by name, which was already serialized on a four-packet handshake and fsync-bound."
    notes: "The comparative bench lane could NOT measure this — it runs MQTTD_DURABLE_SESSIONS=0 with clean sessions, where the 0057 path never executes; a before/after there would have reported a zero delta without running the code (a check that cannot fail). The harness is a dedicated script exercising exactly the changed path. Two anomalies recorded: (1) one warm-up run in the back-to-back sequence failed its 120s window (publisher fully acked, subscriber lagging) and did NOT reproduce in isolation — a virgin-store rerun with warn-level logging delivered all 500 in 22s with zero broker warnings; treated as machine noise, noted here so a recurrence has a trail. (2) run-over-run degradation within a session (rates fall ~30% across three consecutive runs) exists in BOTH binaries, so it is pre-existing store-growth behaviour, not 0057 — worth its own investigation someday. Future headroom: the three metadata writes are three separate snapshot RMWs; batching record with the #124 queue append would remove one fsync per message."

  - id: 0057-T7
    title: "Close the clear-before-truncate hole: the durable outbound ID must OUTLIVE the queued delivery (truncate first, clear second, and not at all if the truncate failed)"
    status: done
    date: 2026-09-07
    issue: 533
    evidence: "REPRODUCED then CLOSED (commits e360f3b, this one). The hole: pub_comp retired the durable outbound id BEFORE truncating the queued delivery, so a crash between the two left the entry in the log with its id record gone — and finish_attach resumes only offsets it still finds in the log, so nothing suppressed the replay. A subscriber that had already answered PUBCOMP was re-sent the message as a FRESH publish, dup=false, under a new packet id (1025 against the original 1) it could not dedup against: a duplicate at QoS 2, violating this ADR's own Acceptance text. NOT an atomic-completion or schema change in the end — the fix is the ORDER. The id record must outlive the queued delivery, so pub_comp truncates first and clears second, and skips the clear entirely when the truncate failed (truncate_acked_now is now #[must_use] and reports it). A crash in the remaining window leaves an id record whose message left the log, which finish_attach ALREADY handles and ADR 0057 already priced in: released phase sends the spurious PUBREL, the subscriber answers PUBCOMP (MQTT-4.3.3), the unconditional clear retires it. Tests: hub::a_completed_qos2_delivery_does_not_replay_when_the_truncate_is_lost, mutation-proven (restoring the old order returns pkid 1025 vs 1), whose oracle asserts IDENTITY not silence — nothing, a bare PUBREL, or the same message under its ORIGINAL id with DUP are all legal QoS 2 recoveries, a different id is not; plus its control ..._when_the_truncate_lands, which passes on both orders and so proves the window is the cause rather than restore-replays-in-general. Full lib suite 365, qos2/qos1/inflight_durability/persistence green. COMPATIBILITY: patch, no break — no API, wire, storage-schema or config change, ordering is node-local so no ADR 0039 skew or rollback implication; the only client-visible change is a spec-legal spurious PUBREL where a QoS 2 duplicate used to be. Still unexercised and tracked in #533: the quorum-replicated backend, and the clearance-FAILURE boundary (a different state, whose orphan tolerance pub_comp documents separately)."
  - id: 0057-T8
    title: "QoS 2 completion, the arms #533 did not exercise: the quorum-replicated backend (including a truncate refused NotOwner / for want of quorum, which must KEEP the outbound id), the clearance-FAILURE boundary (a different state from the one #533 closed), and a guard on contiguous-prefix truncation"
    status: in-progress
    issue: 577
    evidence: "Implementation prepared for review: 14 Hub retirement/recovery regressions plus two metadata concurrency/lock-lifetime tests. Reproduced prefix-blocked completion, failed-write watermark poisoning, repeated-PUBCOMP clearance, orphan retry loss, failed snapshot admission, unmatched-ID prefix loss, and concurrent metadata ID loss. Repairs retain completed/reserved IDs, require explicit quorum-durable retirement, retry cleanup on sweep, fail closed at restore, and serialize metadata RMW per client. Local redb reopen and production group-routed redb replica takeover fixtures pass. Five mutations fail for the expected assertions: lazy quorum retirement, premature clearance, pre-write watermark advance, ID reuse and missing restored offset tracking. Workspace tests pass after making two existing exact-sequence gossip tests use paused time instead of racing periodic snapshots. Awaiting PR review/CI/merge."
    notes: "Split from #533. No wire or disk-schema change, but stronger SessionStore/ReplicatedLog backend contracts default to fail closed. The three-replica transport/lease fixture is not a real Raft/network HA test. Deferred state stays reserved against session quota; retry count is bounded by retained state, not a latency bound. QoS 2 storage waits remain on-loop; #575/#405 isolation and general replay pagination are not delivered here."
