## What is new

- **JWT verification is stricter** (jsonwebtoken 12). A token is refused when its header
  lists a critical extension the broker does not implement (RFC 7515 §4.1.11), or when
  its `iss`, `aud` or `sub` claim has the wrong type. This holds for static-key
  (`MQTTD_JWT_*`) and OIDC verification alike.
- **OIDC: JWKS keys without `alg` are used.** The member is optional (RFC 7517 §4.4). A
  key without it verifies the one allowed algorithm its type implies: RS256 for an RSA
  key, ES256 for a P-256 key. A key published for encryption (`use: enc`) is never used.
- **OIDC: access tokens only, if you want it.** With `MQTTD_OIDC_REQUIRE_AT_JWT=1`
  (`security.oidc.require_at_jwt`), the broker accepts only tokens typed as RFC 9068
  access tokens (header `typ` `at+jwt`), so an ID token cannot stand in for one. It is
  off by default, because most providers do not type their access tokens that way.
- **mqtt-bridge: an upstream outage, a dropped or silent link, or a bridge restart no longer
  loses messages** ([ADR 0060](../adr/0060-bridge-durability-and-ack-contract.md)
  Amendment 1, issue #1103). In 1.3.0 the bridge acknowledged a message at its source when it
  handed it to the destination, not when the destination acknowledged it, so whatever was on
  the wire when a link dropped was lost; its local session ended at every disconnect, so
  what was published during a restart was lost; and it never checked for PINGRESP, so a
  broker that vanished without a reset counted as connected until TCP gave up. Now:
  - traffic from the local cluster is acknowledged there only after the upstream has
    acknowledged it, in order. While the upstream is unreachable the bridge disconnects from
    the local cluster, whose session keeps the messages, so nothing is written to the
    bridge's disk;
  - traffic from an upstream is acknowledged after the local cluster's PUBACK, or after it
    is spooled while the local link is down. A replay deletes each spooled message only once
    the local cluster acknowledges it;
  - a connection that receives nothing for one keepalive interval is closed
    (`keep_alive_secs`, default 30);
  - a far broker's refusal is either final (not authorized, invalid topic or payload format:
    acknowledged, audited, counted as `fss_bridge_dropped_total{reason="refused"}`) or
    retried, backing off from 1 to 30 seconds.
- **mqtt-bridge: one link per upstream.** Each upstream has its own local session, so one that
  is unreachable no longer holds up the others.
- **mqtt-bridge settings:** `[local] session_expiry_secs` (default 4294967295, never),
  `keep_alive_secs` on any endpoint, `max_inflight_bytes` (default 64 MiB, the most one
  direction of a link holds; the bridge stops reading past it), and `session_expiry_secs` on
  an upstream, for a partner broker that allows a persistent session. New metric:
  `fss_bridge_sessions_lost_total`, a reconnect that found the local session gone.
- **Several hub loops on a clustered node** (experimental,
  [ADR 0093](../adr/0093-data-shards-and-a-control-task.md) Amendment 5). In 1.3.0
  `node.hub_shards` (`MQTTD_HUB_SHARDS`) above 1 was refused on a node that names peers.
  Now a clustered node runs them too:
  - shard 0 speaks for the node to its peers, and every shard forwards its own clients'
    publishes and is answered for them;
  - a peer's publishes are spread over the shards and answered once every shard holding a
    copy has stored it;
  - the node's retained values are committed by shard 0, one at a time, as on one loop;
  - the admin API and the gauges cover every shard.

  The default stays one loop.

## Fixed

- **A reconnecting persistent session could lose queued messages past the first 10,000**
  (issue #1235). A reconnect replayed at most 10,000 queued messages and left the rest for
  the next reconnect, while live messages went past them. Once the subscriber had
  acknowledged what it received, the broker treated the unread rest as delivered too and
  deleted it. Now a reconnect replays the whole queue on that connection, 1,000 messages at
  a time as the subscriber makes room, and live messages wait behind the queue, so they
  also arrive in order.

## Upgrading from 1.3.0

### Token verification

Each item below is a security fix that can refuse a token or a configuration 1.3.0
accepted.

- **A configured issuer and audience must be in the token.**
  - **Before:** a token without an `aud` claim passed the audience check, and one without
    `iss` passed the issuer check. This held in OIDC mode, and for static keys with
    `MQTTD_JWT_AUDIENCE` or `MQTTD_JWT_ISSUER` set.
  - **Now:** such a token is refused.
  - **Before you upgrade:** check that the tokens your clients present carry `aud` and
    `iss`. Keycloak, for one, puts this broker's client id in `aud` only through an
    audience mapper on the client.
- **A token is not accepted before its `nbf`.** 1.3.0 ignored the claim. A token whose
  `nbf` lies more than the 60 s clock-skew leeway ahead is now refused (RFC 7519 §4.1.5).
- **`iss` must be a single string.** A token whose `iss` is an array is refused, even one
  that holds the expected issuer (RFC 7519 §4.1.1).
- **An HS256 secret must be at least 32 bytes.**
  - **Before:** `hs256_secret_file` (`MQTTD_JWT_HS256_SECRET_FILE`) could hold a secret of
    any length. A short one can be guessed offline from one captured token. An empty one
    gave a verifier that accepted tokens signed with an empty key, which anyone can mint.
  - **Now:** a secret under 32 bytes (256 bits, RFC 7518 §3.2) after trimming stops the
    broker from starting, and the error names the file. `--check-config --preflight`
    fails the same way, and a reload keeps the running verifier.
  - **Before you upgrade:** replace a shorter secret, for example with the output of
    `openssl rand -base64 32`, and run `mqttd --check-config --preflight` on the host.
- **The OIDC discovery document must name the configured issuer exactly** (OpenID Connect
  Discovery 1.0 §4.3). Otherwise discovery fails, and token authentication stays closed
  until it succeeds. Tokens already had to carry exactly the configured `iss`, so a
  working setup is affected only if its provider's discovery document names the issuer
  differently from its tokens.

### mqtt-bridge

- **With several upstreams, each has its own local session.**
  - A configured `[local] client_id` gets `.<upstream name>` appended, and a generated one
    changes form. Update any broker ACL keyed on the bridge's local client id.
  - Under `ha = "shared"` the `$share` group gets `.<upstream name>` appended.
  - The metrics name each local side `local:<upstream name>`.
  - With one upstream, the client id, share group and metric names are unchanged.
- **Rules that would relay between upstreams are refused.** With one local session per
  upstream, a message brought in from one upstream reaches another upstream's matching `out`
  rule like any local message; 1.3.0's single local connection kept a bridge from forwarding
  it. So a configuration with such a pair of rules now stops the bridge at startup, and the
  error names the pair. **Before you upgrade:** run the new bridge against your configuration.
  Remap the `in` rule's topics to keep the upstreams apart, or set
  `relay_between_upstreams = true` to allow the flow.
- **The local session outlives the bridge.** With the default `session_expiry_secs` it never
  expires, so a bridge you retire leaves its session queueing on the cluster until you delete
  it through the admin API. Set a finite `session_expiry_secs` to have it expire.
- **`out` rules no longer use the spool.** A QoS ≥ 1 `out` rule no longer needs
  `[spool].dir`, and it refuses `[local] session_expiry_secs = 0`. The spool now holds only
  traffic from upstreams, one file per upstream (`spool-local-<i>.redb`).
- **Spools left by 1.3.0 are drained.** `spool-upstream-<i>.redb` is sent to its upstream
  before that link's local session connects; `spool-local.redb` moves into
  `spool-local-0.redb` at startup. Keep `[spool].dir` until they are empty
  (`fss_bridge_spool_depth`).

### Clusters

- **The lease group runs on openraft 0.10, and a rolling upgrade still mixes versions.** Its
  messages between nodes and its `lease.redb` keep 1.3.0's encoding, so 1.3.0 and 1.4.0
  nodes run one lease group while you roll forward or back.
