## What is new

- **A rule engine on the publish path** ([ADR 0083](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0083-rule-engine.md),
  [0084](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0084-watching-and-editing-rules-live.md)).
  EMQX's rule SQL (`SELECT … FROM … WHERE`, `FOREACH … DO … INCASE`), its functions,
  events and `republish` and `console` actions, with EMQX's results (probed against
  EMQX 6.3.1). No data sinks. Rules are a TOML file per node, reloaded on `SIGHUP`. They
  can be watched and edited live: statistics and a trace on `$SYS`, a rules API on the
  admin listener, `mqttd --check-rules`, `mqttd --rule-test`, and a demo under
  `demo/rules-live`. `scripts/migrate/from-emqx.py` carries EMQX rules over.
- **`jq` and your own functions in a WebAssembly sandbox**
  ([ADR 0086](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0086-wasm-rule-functions.md)).
  `jq/2` and `jq/3` run jq 1.8.1 compiled to WebAssembly, with EMQX's results. A rules
  file can declare WebAssembly modules of your own, each pinned by its SHA-256. Every
  call is bounded in time, memory, stack and output. Off by default.
- **State for rules**
  ([ADR 0085](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0085-rule-state-store.md)).
  EMQX's `kv_store_*` and `proc_dict_*`, and mqttd's own `kv_*` functions on keys in
  declared namespaces: counters, sets, first and last values, distinct counts, TTLs,
  "held for N seconds", change detection, counting a message once. A namespace is
  `local` to a node or `eventual` (held by every member, converging by merge). A key's
  expiry is an event, `$events/state/expired`, which makes "silent for X" a rule.
  Operators see and manage state through the admin API and `mqttd --admin`.
  `mqttd --rule-test --sequence` replays a file of messages on a driven clock.

Start with [docs/RULES.md](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/RULES.md)
and the [rule cookbook](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/RULES-COOKBOOK.md).

## Upgrading from 1.1.0

A rolling upgrade, one node at a time, as for any minor (ADR 0039). No store's schema
version changed, so there is no migration.

**Three client-visible behaviours change for every broker, with or without rules**
(ADR 0084):

- **`$SYS` is the broker's.** A client PUBLISH or a Will to `$SYS` or anything under
  `$SYS/` is refused whatever the ACL says (MQTT 5: `0x87`; 3.1.1: dropped), and a Will
  there refuses the CONNECT. The one exception is `$SYS/broker/connection/<id>/state`,
  where a Mosquitto bridge with notifications on reports its state: the ACL decides it
  as before. A bridge whose `notification_topic` points elsewhere under `$SYS/` must
  move it or set `notifications false`. Retained `$SYS/…` messages that clients stored
  before the upgrade are cleared by the node that owns them in the first minute after
  it starts (the count is logged at WARN) and are never replayed meanwhile.
- **A subscribe deny also applies inside `$share`.** A deny on `a/#` now refuses
  `$share/g/a/b`, where an allow on `$share/…` used to admit it.
- **A broad `$share` allow no longer reaches `$`-topics.** `$share/+/#` and `$share/#`
  do not grant `$share/g/$SYS/…`; the allow must name the `$` level inside its `$share`
  pattern (`$share/+/$SYS/brokers/+/rules/#`).

`mqttd --admin authz <subject> <publish|subscribe> <topic>` answers how the upgraded
broker decides a given case.

What else to know:

- **The peer protocol goes from 12 to 14.** Both steps are additive, and `proto_min`
  stays 6. A cluster that runs no rules puts nothing new on the wire. Protocol 13
  carries a message's publisher to a member whose rules select a message event;
  protocol 14 carries the state of `eventual` namespaces. During the roll a 1.1.0 node
  runs no rules, holds no state and is sent none, and a 1.2.0 node reports messages
  forwarded from it with an unknown publisher. **Upgrade every node first, then deploy
  rules files**, the same file on every node.
- **While the roll lasts the `$SYS` reservation is partial.** A 1.1.0 node still accepts
  client publishes to `$SYS/…` and forwards them; a 1.2.0 node drops such a forward when
  it would be retained, is QoS 1 or 2, or names that node, and delivers the rest.
- **Rolling back.** `MQTTD_RULES_*` variables are ignored by 1.1.0 without a word. A
  `[rules]` table in the configuration file is an unknown key to 1.1.0, which refuses to
  start on it unless `runtime.config_unknown_keys = "warn"`
  (`MQTTD_CONFIG_UNKNOWN_KEYS=warn`) is set for the window.
- **Building from source needs Rust 1.96** (was 1.88): the WebAssembly runtime requires
  it. `mqttd-operator` still builds with 1.89. Release binaries are unaffected.
- **The binary is larger.** A static, stripped `aarch64-unknown-linux-musl` build of this
  tree is 24.3 MB, and 16.9 MB when built with `--no-default-features`, which leaves the
  WebAssembly runtime and the jq module out (7.4 MB). The 1.1.0 release binary for that
  target was 14.7 MB. Those two builds were made on a development machine, not by the
  release recipe; the sizes of this release's own binaries are in the asset list below.
  On x86_64 the runtime's share is about 3 MB more.

### If you switch `jq` on, or declare a module

`jq` is off unless `rules.jq = true` (`MQTTD_RULES_JQ=1`); a rules file that calls it
then does not load. The setting is read at startup, on every node. A module needs no
switch: declaring a `[functions.<name>]` table is the switch.

Compiled WebAssembly needs memory the process may map executable. **Under the shipped
systemd unit that is forbidden**, so on every node that will run such rules add a
drop-in (`sudo systemctl edit mqttd`) and restart:

```ini
[Service]
MemoryDenyWriteExecute=false
```

The unit file itself is unchanged and stays hardened; do not edit it. The container
image and the Helm chart impose no such restriction and need no change. If you forget
the drop-in nothing crashes: a rules file that calls `jq` or declares a module fails to
load and says why. At a start that means the broker exits with that error; at a reload
the running rules stay. `mqttd --check-config` run under the unit's settings says which
host it is on. What you give up, and how to bound what `jq` and modules can cost, is in
`docs/HARDENING.md` (H-7.12 to H-7.15) and `deploy/systemd/README.md`.

## New configuration

All under `[rules]`; none is set by default, and without `rules.file` there is no rule
engine. The full text is in `docs/CONFIGURATION.md`.

| Key | Environment | Default | What it does |
|---|---|---|---|
| `rules.file` | `MQTTD_RULES_FILE` | unset | The rules file. Reloaded on `SIGHUP` |
| `rules.sys_interval_secs` | `MQTTD_RULES_SYS_INTERVAL` | `0` (off) | Seconds between rule statistics on `$SYS` |
| `rules.trace` | `MQTTD_RULES_TRACE` | `false` | The rule trace on `$SYS`. It copies payloads: read HARDENING H-7.9 first |
| `rules.trace_rate` | `MQTTD_RULES_TRACE_RATE` | `20` | Trace records per rule per second |
| `rules.admin_writers` | `MQTTD_RULES_ADMIN_WRITERS` | none | Admin certificate subjects that may write the rules file through the admin API |
| `rules.jq` | `MQTTD_RULES_JQ` | `false` | Switches `jq/2` and `jq/3` on. Read at startup |
| `rules.jq_default_timeout_ms` | `MQTTD_RULES_JQ_DEFAULT_TIMEOUT_MS` | `10000` | `jq/2`'s timeout, as in EMQX. Read at startup |
| `rules.jq_env` | `MQTTD_RULES_JQ_ENV` | none | Environment variables a jq program may read. Read at startup |
| `rules.functions_env` | `MQTTD_RULES_FUNCTIONS_ENV` | none | Environment variables a module may be shown. Read at startup |
| `rules.function_max_ms` | `MQTTD_RULES_FUNCTION_MAX_MS` | `10000` | No jq or module call runs longer, whatever a rule or a payload asks for. Read at startup |
| `rules.state_max_bytes` | `MQTTD_RULES_STATE_MAX_BYTES` | 256 MiB | Ceiling for all rule state on a node; `0` switches state off. Read at startup |
| `rules.state_expiry_per_sec` | `MQTTD_RULES_STATE_EXPIRY_PER_SEC` | `1000` | Pace of `$events/state/expired`. Read at startup |

Also new on the admin API: the rules routes (`/admin/v1/rules…`) and the rule state
routes (`/admin/v1/rules/state…`), and the audit kinds `rules.write` and `state.delete`
(`docs/AUDIT-SCHEMA.md`; new kinds are additive, as promised).

## Where mqttd differs from EMQX

Listed in full in `docs/RULES.md`, "Differences from EMQX". The ones most likely to
matter when porting rules:

- Actions are `republish` and `console`. A rule that names a data sink does not load.
- Limits EMQX does not have: on rule state, on `jq` and module calls, on regular
  expressions, on what one message's functions may build, and on the size of an integer.
- `jq` is off by default, and `$ENV` in jq is empty unless the operator lists variables
  (`rules.jq_env`).
- A chain of rules republishing into each other stops 32 republishes deep.
- `proc_dict_*` is one dictionary per connection, bounded, and empty for a Will and for
  events about a session that has no connection.
- Conditions EMQX fails on every message and mqttd evaluates (`x NOT IN (…)`, a bare
  value as a condition). A rule relying on them does not port back to EMQX.
- The `kv_*` functions, `[state.<name>]`, `$events/state/expired` and
  `[functions.<name>]` are mqttd's own; EMQX has none of them.

## Known limits of this release

- **A node that holds a member dead and cannot reach it for eight seconds acknowledges
  QoS 1 and QoS 2 publishes for that member's subscribers and does not deliver them**
  (#973) — a partition between the two that outlasts the verdict by that long. Until
  then, and for as long as the link between them is merely down, such a publish is held:
  its publisher waits, and it is delivered when the link is back. A verdict that is
  wrong while the network works costs half a second, because the node keeps dialing a
  member it holds dead; `mqttd_publish_held_for_unreachable` counts what is being held.
  Past the eight seconds the publisher gets a normal acknowledgement and no counter
  records the loss; `mqttd_members{state="dead"}` shows the verdict. One narrower case
  remains inside them: a clean-session subscriber on a member wrongly held dead loses a
  publish if another node starts announcing the same subscription before the link is
  back. A healthy formation produces no such verdict; an outage of one member shorter
  than the suspicion window can, in a cluster of about ten nodes or more (#975). The
  rest of the fix — a held publish resolved only by evidence or by confirmation that
  the member is gone — is designed in ADR 0087 and is not in this release.
- **Rule state is in memory.** A node that restarts comes back empty and, for `eventual`
  namespaces, is filled again by the other members; when every node stops, it is gone.
  No backup carries it. A snapshot to disk is planned.
- **`strong` consistency is not built**; a namespace that asks for it is refused at load.
  In an `eventual` namespace a message can be counted once per node inside the
  replication lag, and nodes hold differing copies while a namespace is at its bounds.
- **Concurrent long `jq` or module calls are bounded in time each**
  (`rules.function_max_ms`), **not in number.** Set a memory limit on the process.
- **Deleting state through the admin API is one key per request.** Purging a namespace
  and changing the expiry of stored keys are planned.
- With `jq` on or a module declared, a compiler (wasmtime's Cranelift) is in the
  broker's trust base, and three C libraries (PCRE2, zlib, liblz4) run in-process for the
  rule functions that need them. `docs/THREAT-MODEL.md` has the accepted risks.

## Cost

Microbenchmarks on one Apple M1 Pro, 2026-10-12, not idle (load average 9 to 21), the
fastest of three rounds. Not a cluster benchmark.

- Rules that use neither `jq` nor state cost what they did before those were added (the
  commit before both against this tree, alternating rounds): a publish no rule selects
  86.4 and 85.9 ns; a `WHERE` that rejects 751 and 756 ns; a `WHERE` that passes with
  one republish 1,399 and 1,401 ns; `SELECT *` with a JSON republish 3,749 and 3,715 ns;
  a `FOREACH` over ten elements 6,342 and 6,435 ns. Between 0.9% faster and 1.5% slower.
- A publish through one rule: 1.40 µs without state, 1.76 µs with a `kv_incr`, 2.23 µs
  with an idempotency key, 1.84 µs with a `kv_incr` in an `eventual` namespace.
- Between two nodes on loopback, a write was readable on the other node 1.3 ms later,
  and a peer caught up on 100,000 keys in 89 ms.

## Also in this release

- **Clusters above about ten nodes form without a storm of false suspicions, and a
  member falsely declared dead comes back** (#971). With signed gossip, two nodes that
  were not each other's seed used to drop each other's datagrams until one happened to
  send the other its full certificate; at 12 and 14 nodes that meant dozens of false
  `SUSPECT` and several false `DEAD` per broker during formation, minutes to settle,
  and at worst a pair in which one broker held the other out for good. A node now shows
  its certificate on the first datagram to each peer and again when a peer restarts,
  asks for a certificate it lacks, and greets a member once as it forgets it. In
  simulation a 14-node formation settles in 8 s (12 s at worst) with no false
  suspicion, where 1.1.0 took 215 s and did not settle within five minutes in a quarter
  of the runs; a member falsely declared dead is back within 30 s. The gossip wire
  format is unchanged and a 1.1.0 node interoperates, but nodes still on 1.1.0 keep the
  old behaviour among themselves until they are upgraded. New counter:
  `mqttd_gossip_cert_requests_total`, the certificate requests a node has sent
  (ADR 0022 and ADR 0016, amendments of 2026-10-12).
- A reload sent very early in startup no longer ends the broker: `SIGHUP` is registered
  at startup, with the stop signals (#954).
- Durable-path instrumentation: sampled transit stages on the peer link, and its
  `write_wait` counter.
- Bench rig: NIC counters, the peer bus over the public network, lane E ladder fixes.
- Eleven dependency update pull requests.
