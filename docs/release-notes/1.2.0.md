## What is new

- **A rule engine on the publish path** ([ADR 0083](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0083-rule-engine.md),
  [0084](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0084-watching-and-editing-rules-live.md)).
  EMQX's rule SQL (`SELECT … FROM … WHERE`, `FOREACH … DO … INCASE`), functions, events
  and the `republish` and `console` actions, with EMQX's results (probed against EMQX
  6.3.1). No data sinks. Rules are a TOML file per node, reloaded on `SIGHUP`. Watch and
  edit them live: statistics and a trace on `$SYS`, a rules API on the admin listener,
  `mqttd --check-rules` and `mqttd --rule-test`. A demo is in `demo/rules-live`, and
  `scripts/migrate/from-emqx.py` carries EMQX rules over.
- **`jq` and your own functions in a WebAssembly sandbox**
  ([ADR 0086](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0086-wasm-rule-functions.md)).
  `jq/2` and `jq/3` run jq 1.8.1, with EMQX's results. A rules file can declare
  WebAssembly modules of your own, each pinned by its SHA-256. Every call is bounded in
  time, memory, stack and output. Off by default.
- **State for rules, experimental**
  ([ADR 0085](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0085-rule-state-store.md)).
  EMQX's `kv_store_*` and `proc_dict_*`, and mqttd's own `kv_*` functions in declared
  namespaces: counters, sets, first and last values, distinct counts, TTLs, "held for N
  seconds", change detection, counting a message once. A namespace is `local` to a node or
  `eventual` (held by every member, merged). A key's expiry raises
  `$events/state/expired`, so "silent for X" is a rule. Manage state through the admin
  API and `mqttd --admin`; replay a message sequence with `mqttd --rule-test --sequence`.
  State is in memory and experimental until it is durable (see Known limits).

Start with [docs/RULES.md](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/RULES.md)
and the [rule cookbook](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/RULES-COOKBOOK.md).

## Upgrading from 1.1.0

A rolling upgrade, one node at a time (ADR 0039). No store schema changed, so there is
no migration. On Kubernetes, `helm upgrade` or the operator rolls the pods. For systemd
hosts and Compose, `scripts/roll-upgrade.sh` does it: see `docs/OPERATIONS.md`, "Rolling
upgrades".

**Three client-visible changes for every broker, with or without rules** (ADR 0084):

- **`$SYS` is the broker's.** A client PUBLISH or Will to `$SYS` or below is refused
  whatever the ACL says (MQTT 5: `0x87`; 3.1.1: dropped). A Will there refuses the
  CONNECT. The exception is `$SYS/broker/connection/<id>/state`, a Mosquitto bridge's
  notification topic, which the ACL decides as before. A bridge notifying elsewhere under
  `$SYS/` must move it or set `notifications false`. Retained `$SYS/…` messages stored by
  clients are cleared within a minute of startup (count logged at WARN) and never replayed.
- **A subscribe deny also applies inside `$share`.** A deny on `a/#` now refuses
  `$share/g/a/b`.
- **A broad `$share` allow no longer reaches `$`-topics.** `$share/+/#` does not grant
  `$share/g/$SYS/…`; name the `$` level in the pattern (`$share/+/$SYS/brokers/+/rules/#`).

`mqttd --admin authz <subject> <publish|subscribe> <topic>` shows how the upgraded broker
decides a case.

Also:

- **Peer protocol 12 → 14**, both steps additive; `proto_min` stays 6. A cluster without
  rules sends nothing new. Protocol 13 carries a message's publisher for message events;
  14 carries `eventual` state. During the roll a 1.1.0 node runs no rules and holds no
  state. **Upgrade every node first, then deploy the rules file**, the same on every node.
- **During the roll the `$SYS` reservation is partial.** A 1.1.0 node still accepts and
  forwards client publishes to `$SYS/…`. A 1.2.0 node drops such a forward if it is
  retained, QoS 1 or 2, or names that node, and delivers the rest.
- **Rolling back.** 1.1.0 ignores `MQTTD_RULES_*` silently, but refuses to start on a
  `[rules]` table unless `runtime.config_unknown_keys = "warn"`
  (`MQTTD_CONFIG_UNKNOWN_KEYS=warn`) is set.
- **A peer link ends when its certificate expires** (ADR 0088). Before, an expired peer
  certificate kept working. Now the link ends within about 2 s of the earlier `notAfter`,
  with no grace and no setting, and the cluster bus no longer resumes TLS sessions. A
  `notBefore` up to 60 s ahead is accepted for clock skew.
  - An ended link is a lost link, not a dead node. After a renewal and `SIGHUP`, links move
    to the new certificate one at a time before the old one ends, so renewing loses no link.
  - Counted in `mqttd_revocation_evictions_total{reason="peer-cert-expired"|"own-cert-expired"}`.
    Before the roll, check `mqttd_tls_expiry_seconds{role="peer"}`.
- **`gen-certs.sh` needs a stated lifetime.** `node` and `renew` take
  `--lifetime <N>h|<N>d|<N>m` (or `LEAF_LIFETIME`); without one they exit 2 and write
  nothing. The 365-day default is gone. New commands: `renew`, `revoke`. The chart's
  `bootstrap.sh` has no `LEAF_DAYS` default either. Add the lifetime to scripts that call
  them.
- **Building from source needs Rust 1.96** (was 1.88), for the WebAssembly runtime.
  `mqttd-operator` still builds with 1.89. Release binaries are unaffected.
- **The binary is larger.** The `x86_64-unknown-linux-musl` build by the release recipe is
  33.5 MB (1.1.0: 18.7 MB). On aarch64 a development build is 24.3 MB (1.1.0: 14.7 MB), and
  16.9 MB with `--no-default-features`, which leaves out the WebAssembly runtime and jq.
  The asset list below has this release's sizes.

### If you switch `jq` on, or declare a module

`jq` is off unless `rules.jq = true` (`MQTTD_RULES_JQ=1`), read at startup on every node.
Without it, a rules file that calls `jq` does not load. Declaring a `[functions.<name>]`
table switches modules on.

Compiled WebAssembly needs executable memory, which **the shipped systemd unit forbids**.
On every node that runs such rules, add a drop-in (`sudo systemctl edit mqttd`) and
restart:

```ini
[Service]
MemoryDenyWriteExecute=false
```

Leave the unit file itself unchanged. The container image and Helm chart need nothing.
Without the drop-in nothing crashes: the rules file fails to load and says why. At startup
the broker exits; on reload the running rules stay. `mqttd --check-config` under the unit
reports it. The trade-offs are in `docs/HARDENING.md` (H-7.12 to H-7.15) and
`deploy/systemd/README.md`.

## New configuration

The rule engine's keys are under `[rules]`. None is set by default; without `rules.file`
there is no rule engine. Full text: `docs/CONFIGURATION.md`.

| Key | Environment | Default | What it does |
|---|---|---|---|
| `rules.file` | `MQTTD_RULES_FILE` | unset | The rules file. Reloaded on `SIGHUP` |
| `rules.sys_interval_secs` | `MQTTD_RULES_SYS_INTERVAL` | `0` (off) | Seconds between rule statistics on `$SYS` |
| `rules.trace` | `MQTTD_RULES_TRACE` | `false` | The rule trace on `$SYS`. It copies payloads: read HARDENING H-7.9 first |
| `rules.trace_rate` | `MQTTD_RULES_TRACE_RATE` | `20` | Trace records per rule per second |
| `rules.admin_writers` | `MQTTD_RULES_ADMIN_WRITERS` | none | Admin certificate subjects that may write the rules file through the admin API |
| `rules.jq` | `MQTTD_RULES_JQ` | `false` | Switches `jq/2` and `jq/3` on. Read at startup |
| `rules.jq_default_timeout_ms` | `MQTTD_RULES_JQ_DEFAULT_TIMEOUT_MS` | `10000` | `jq/2`'s timeout, as in EMQX. Read at startup |
| `rules.jq_env` | `MQTTD_RULES_JQ_ENV` | none | Environment variables a jq program may read. Read at startup |
| `rules.functions_env` | `MQTTD_RULES_FUNCTIONS_ENV` | none | Environment variables a module may be shown. Read at startup |
| `rules.function_max_ms` | `MQTTD_RULES_FUNCTION_MAX_MS` | `10000` | No jq or module call runs longer. Read at startup |
| `rules.state_max_bytes` | `MQTTD_RULES_STATE_MAX_BYTES` | 256 MiB | Ceiling for all rule state on a node; `0` switches state off. Read at startup |
| `rules.state_expiry_per_sec` | `MQTTD_RULES_STATE_EXPIRY_PER_SEC` | `1000` | Pace of `$events/state/expired`. Read at startup |

Under `[tls]` (ADR 0088), read at startup:

| Key | Environment | Default | What it does |
|---|---|---|---|
| `tls.expiry_warn_permille` | `MQTTD_TLS_EXPIRY_WARN_PERMILLE` | `667` | Share of a certificate's, CA's or CRL's lifetime spent before the broker warns |
| `tls.end_sessions_at_cert_expiry` | `MQTTD_TLS_END_SESSIONS_AT_CERT_EXPIRY` | `false` | End a client session when its certificate passes `notAfter` |

The chart gains `secrets.peerTls.certManager` and the operator
`spec.secrets.peerTlsCertManager` (`duration` and `renewBefore` required), for peer
certificates from cert-manager's csi-driver.

New on the admin API: the rules routes (`/admin/v1/rules…`), the rule state routes
(`/admin/v1/rules/state…`), and the audit kinds `rules.write` and `state.delete`
(`docs/AUDIT-SCHEMA.md`).

## Where mqttd differs from EMQX

The full list is in `docs/RULES.md`, "Differences from EMQX". The ones that matter most
when porting:

- Actions are `republish` and `console`. A rule naming a data sink does not load.
- Limits EMQX lacks: on rule state, `jq` and module calls, regular expressions, what one
  message's functions may build, and integer size.
- `jq` is off by default, and `$ENV` is empty unless `rules.jq_env` lists variables.
- A chain of rules republishing into each other stops 32 deep.
- `proc_dict_*` is one bounded dictionary per connection, empty for a Will and for events
  of a session with no connection.
- mqttd evaluates some conditions EMQX fails on every message (`x NOT IN (…)`, a bare
  value as a condition). Rules relying on them do not port back.
- `kv_*`, `[state.<name>]`, `$events/state/expired` and `[functions.<name>]` are mqttd's
  own.

## Known limits of this release

- **A node that holds a member dead and cannot reach it for 8 s acknowledges, without
  delivering, QoS 1 and 2 publishes for that member's subscribers** (#973, with durable
  sessions, the default). Until then, and while the link is merely down, such publishes
  are held and delivered when the link returns.
  - `mqttd_publish_held_for_unreachable` counts what is held. Past 8 s the publisher is
    acked and the publish counted in
    `mqttd_publish_resolved_undeliverable_total{reason="hold-expired"}`.
  - With `MQTTD_DURABLE=0` there is no 8 s bound. The publish is held until membership
    confirms the member gone (30 s after the verdict, or a restart under its node id),
    then acked and counted (`reason="peer-gone"` or `"no-shared-member"`).
  - A persistent session on such a node is treated as gone with it. If the node returns
    with its disk, it lacks what was published meanwhile.
  - With durable sessions, a subscriber on a member wrongly held dead loses a publish if
    another subscription to its topic appears before the link returns.
  - A wrong verdict costs about half a second while the network works, because the node
    keeps dialing. It can follow an outage of 2 s or more (rare at 2.5 s, up to one run in
    four at 3 s in simulation), sustained packet loss on the cluster network, or, during
    the roll, an outage from 0.5 s while nodes are on 1.1.0 (#975).
  - During the roll, a 1.1.0 node may still ack a `$share` message for a consumer that
    left milliseconds earlier. A 1.2.0 refusal sends a 1.1.0 node's `$share` message to
    another member. With none left, it refuses the publisher as in a brownout and logs
    `refusal=brownout`.
  - The rest of the fix (ADR 0087 D8, 0087-T5) is designed, not shipped.
- **A minority side of a partition can acknowledge a durable QoS 1 publish and lose it at
  the heal** (#1030). A lease holder cut off with enough of a group's replicas keeps
  writing while the majority reassigns the group. At the heal its writes are superseded. A
  node that is down, or one lost link, does not cause it. A fix is being designed.
- **A node whose session scans never complete holds some QoS 1 acks indefinitely**
  (#1049). If it cannot read one durable session it owns (`NoQuorum`, repeatedly), it
  holds the PUBACK of every publish matching no session it knows. `/readyz` stays ready
  and a restart does not clear it.
  - Each incomplete scan is logged at WARN (`session scan incomplete`, naming the sessions
    and why), and `session scan complete again` marks the end.
  - Seen once in the field, under heavy churn at two replicas; not reproduced yet.
    Mitigation: send QoS 1 publishers to the other nodes, which ack normally.
- **QoS 1 messages re-sent after a node dies, or after a connection moves to its session's
  owner, arrive as new messages** (#1058): `DUP` 0, a new packet id. Nothing is lost. QoS 2
  is not affected (ADR 0057). A durable record of what was sent is planned.
- **During a session's ownership move, a publish the old owner refuses may already have
  reached the new owner's live subscribers** (#1054). Each retry reaches them again until
  the old owner lets go, usually within a second. Nothing is lost.
- **Rule state is experimental, because it is in memory.** A restarted node comes back
  empty; `eventual` namespaces are refilled by the other members. When every node stops,
  it is gone, and no backup carries it.
  - Every rules file that uses state loads with a warning saying so.
  - Until state is durable (a snapshot, then `strong`), its functions, `[state.<name>]`
    and admin routes may change in a minor release. The rest of the rule engine is stable.
- **`strong` consistency is not built**; a namespace asking for it is refused at load. In
  an `eventual` namespace a message can be counted once per node within the replication
  lag, and copies differ while a namespace is at its bounds.
- **Long `jq` or module calls are bounded in time each** (`rules.function_max_ms`), **not
  in number.** Set a memory limit on the process.
- **The admin API deletes state one key per request.** Purging a namespace and changing
  stored expiries are planned.
- With `jq` or a module on, wasmtime's Cranelift compiler and three C libraries (PCRE2,
  zlib, liblz4) run in-process. `docs/THREAT-MODEL.md` lists the accepted risks.

## Cost

Microbenchmarks on one Apple M1 Pro, 2026-10-12, not idle (load 9 to 21), fastest of
three rounds. Not a cluster benchmark.

- Rules using neither `jq` nor state cost what they did before (prior commit vs this
  tree, within 1.5%):

  | Case | Before | Now |
  |---|---|---|
  | No rule selects the publish | 86.4 ns | 85.9 ns |
  | `WHERE` rejects | 751 ns | 756 ns |
  | `WHERE` passes, one republish | 1,399 ns | 1,401 ns |
  | `SELECT *`, JSON republish | 3,749 ns | 3,715 ns |
  | `FOREACH` over ten elements | 6,342 ns | 6,435 ns |
- One rule: 1.40 µs without state, 1.76 µs with `kv_incr`, 2.23 µs with an idempotency
  key, 1.84 µs with `kv_incr` in an `eventual` namespace.
- Two nodes on loopback: a write was readable on the other node in 1.3 ms, and a peer
  caught up on 100,000 keys in 89 ms.

## Also in this release

- **Wills follow MQTT 5 more closely** (#1048). A Will carries its Message Expiry
  Interval. Taking a session over within the Will Delay no longer publishes the old Will.
  A Clean Start session with a non-zero expiry and no subscriptions is now kept, as the
  spec requires. A rules-live suite checks every Will case on MQTT 3.1.1 and 5, in CI
  (#1036).
- **An outbound Topic Alias is taken back when its PUBLISH is dropped as too large**
  (#1047). Before, the next PUBLISH named an alias the client never saw.
- **Readiness waits for the first lease** (#1050). A freshly founded node is ready only
  once a lease exists, so the first retained writes and persistent sessions no longer
  fail.
- **A publish forwarded during a lease takeover reaches the session that just moved**
  (#1053). The taking-over node used to ack at once while the session was still loading,
  so it missed the message. It now answers after its next scan lands, and hands the
  publish to the sessions that scan brought.
- **A resumed session is not re-sent messages it already acknowledged** (#1057), when an
  older QoS 2 release was held back after a node failure.
- **The independent history checker judges more of MQTT** (#1039): QoS 2 exactly once,
  protocol errors, Wills owed and not owed, Session Present across clean start and expiry.
- **Certificate lifetimes are visible** (ADR 0088). `mqttd_tls_expiry_seconds{role}` and
  `mqttd_tls_lifetime_spent_ratio{role}` cover every certificate, CA bundle and CRL. A
  WARN fires at `tls.expiry_warn_permille`, an ERROR at expiry, and the chart ships an
  alert.
- **wasmtime 49.0.4** (#1060), for RUSTSEC-2026-0378 and RUSTSEC-2026-0379. The second, a
  Cranelift aarch64 miscompile, applies to `jq` and modules on arm64.
- **Clusters above ten nodes form without false suspicions, and a member wrongly declared
  dead comes back** (#971).
  - With signed gossip, non-seed peers used to drop each other's datagrams until a full
    certificate arrived. At 12 to 14 nodes that meant false `SUSPECT` and `DEAD` verdicts
    and minutes to settle.
  - A node now sends its certificate on first contact and after a peer restarts, and asks
    for a missing one. In simulation 14 nodes settle in 8 s (12 s worst; 1.1.0: 215 s),
    and a wrongly evicted member returns within 30 s.
  - The wire format is unchanged; 1.1.0 nodes keep the old behaviour among themselves.
    New counter: `mqttd_gossip_cert_requests_total` (ADR 0022, ADR 0016).
- **A member silent for a moment is no longer declared dead** (#975, #999).
  - A node used to declare a suspect dead when its suspicion window (4 s, 1.5 s with three
    suspecting) ran out. In simulation a 1.5 s silence got a member declared dead in half
    the runs at 14 nodes.
  - A node now asks the suspect once more, directly, first. No member silent up to 2 s
    (less twice the network latency) is declared dead at 3 to 30 nodes; in a real test,
    none in 68 stops.
  - The price: a real death is seen about 0.3 s later (5.6 s median at 14 nodes, 8.3 s
    worst). No setting and no wire change; during the roll the benefit arrives node by
    node (ADR 0016).
  - A node that was itself stalled reads what arrived meanwhile before concluding
    anything (#1002).
  - New metrics: `mqttd_swim_last_probes_total{outcome}` (`sent`, `spared`, `silent`),
    `mqttd_swim_stalls_total`, `mqttd_swim_stalled_milliseconds_total`, and
    `mqttd_swim_awareness` (0 when healthy).
- **`scripts/roll-upgrade.sh`: a rolling upgrade outside Kubernetes**, for systemd hosts
  over ssh, the Compose deployment, or your own commands. It refuses a skipped minor and a
  cluster that is not ready, and stops at the first node that does not come back.
- A reload very early in startup no longer ends the broker (#954).
- Durable-path instrumentation: sampled transit stages on the peer link and its
  `write_wait` counter.
- Bench rig: NIC counters, the peer bus over the public network, lane E ladder fixes.
- Eleven dependency updates.
