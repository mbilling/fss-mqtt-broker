## What is new

- **A rule engine on the publish path** ([ADR 0083](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0083-rule-engine.md),
  [0084](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0084-watching-and-editing-rules-live.md)).
  EMQX's rule SQL (`SELECT … FROM … WHERE`, `FOREACH … DO … INCASE`), its functions,
  events and `republish` and `console` actions, with EMQX's results (probed against
  EMQX 6.3.1). No data sinks. Rules are a TOML file per node, reloaded on `SIGHUP`. They
  can be watched and edited live: statistics and a trace on `$SYS`, a rules API on the
  admin listener, `mqttd --check-rules`, `mqttd --rule-test`, and a demo under
  `demo/rules-live`. `scripts/migrate/from-emqx.py` carries EMQX rules over.
- **`jq` and your own functions in a WebAssembly sandbox**
  ([ADR 0086](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0086-wasm-rule-functions.md)).
  `jq/2` and `jq/3` run jq 1.8.1 compiled to WebAssembly, with EMQX's results. A rules
  file can declare WebAssembly modules of your own, each pinned by its SHA-256. Every
  call is bounded in time, memory, stack and output. Off by default.
- **State for rules, experimental**
  ([ADR 0085](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/adr/0085-rule-state-store.md)).
  EMQX's `kv_store_*` and `proc_dict_*`, and mqttd's own `kv_*` functions on keys in
  declared namespaces: counters, sets, first and last values, distinct counts, TTLs,
  "held for N seconds", change detection, counting a message once. A namespace is
  `local` to a node or `eventual` (held by every member, converging by merge). A key's
  expiry is an event, `$events/state/expired`, which makes "silent for X" a rule.
  Operators see and manage state through the admin API and `mqttd --admin`.
  `mqttd --rule-test --sequence` replays a file of messages on a driven clock.
  The store is held in memory and is **experimental** until it is durable: a rules file
  that uses it loads with a warning, and its functions, settings and admin routes may
  still change in a minor release (see Known limits).

Start with [docs/RULES.md](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/RULES.md)
and the [rule cookbook](https://github.com/mbilling/fss-mqtt-broker/blob/v1.2.0/docs/RULES-COOKBOOK.md).

## Upgrading from 1.1.0

A rolling upgrade, one node at a time, as for any minor (ADR 0039). No store's schema
version changed, so there is no migration.

**Three client-visible behaviours change for every broker, with or without rules**
(ADR 0084):

- **`$SYS` is the broker's.** A client PUBLISH or a Will to `$SYS` or anything under
  `$SYS/` is refused whatever the ACL says (MQTT 5: `0x87`; 3.1.1: dropped), and a Will
  there refuses the CONNECT. The one exception is `$SYS/broker/connection/<id>/state`,
  where a Mosquitto bridge with notifications on reports its state: the ACL decides it
  as before. A bridge whose `notification_topic` points elsewhere under `$SYS/` must
  move it or set `notifications false`. Retained `$SYS/…` messages that clients stored
  before the upgrade are cleared by the node that owns them in the first minute after
  it starts (the count is logged at WARN) and are never replayed meanwhile.
- **A subscribe deny also applies inside `$share`.** A deny on `a/#` now refuses
  `$share/g/a/b`, where an allow on `$share/…` used to admit it.
- **A broad `$share` allow no longer reaches `$`-topics.** `$share/+/#` and `$share/#`
  do not grant `$share/g/$SYS/…`; the allow must name the `$` level inside its `$share`
  pattern (`$share/+/$SYS/brokers/+/rules/#`).

`mqttd --admin authz <subject> <publish|subscribe> <topic>` answers how the upgraded
broker decides a given case.

What else to know:

- **The peer protocol goes from 12 to 14.** Both steps are additive, and `proto_min`
  stays 6. A cluster that runs no rules puts nothing new on the wire. Protocol 13
  carries a message's publisher to a member whose rules select a message event;
  protocol 14 carries the state of `eventual` namespaces. During the roll a 1.1.0 node
  runs no rules, holds no state and is sent none, and a 1.2.0 node reports messages
  forwarded from it with an unknown publisher. **Upgrade every node first, then deploy
  rules files**, the same file on every node.
- **While the roll lasts the `$SYS` reservation is partial.** A 1.1.0 node still accepts
  client publishes to `$SYS/…` and forwards them; a 1.2.0 node drops such a forward when
  it would be retained, is QoS 1 or 2, or names that node, and delivers the rest.
- **Rolling back.** `MQTTD_RULES_*` variables are ignored by 1.1.0 without a word. A
  `[rules]` table in the configuration file is an unknown key to 1.1.0, which refuses to
  start on it unless `runtime.config_unknown_keys = "warn"`
  (`MQTTD_CONFIG_UNKNOWN_KEYS=warn`) is set for the window.
- **A peer link ends when a certificate it was admitted under expires** (ADR 0088).
  Until now an expired peer certificate went on working: with unsigned gossip the link
  stayed up, and with signed gossip it came back on a resumed TLS session. Now the link
  ends within about two seconds of the earlier `notAfter` of the two certificates, with
  no grace period and no setting, and the cluster bus neither dials nor accepts with
  expired material (it no longer resumes TLS sessions). A `notBefore` up to 60 s ahead
  is accepted, for clock skew. The ended link is handled as a lost link, not as a dead
  node. After a renewal and `SIGHUP`, each link moves to the new certificate on its
  own, one at a time, before the old one ends, so a renewal costs no link loss. Counted
  in `mqttd_revocation_evictions_total{reason="peer-cert-expired"|"own-cert-expired"}`.
  Check your peer certificates' end dates before the roll:
  `mqttd_tls_expiry_seconds{role="peer"}` says how long each has left.
- **`gen-certs.sh` mints nothing without a stated lifetime.** `node` and `renew` need
  `--lifetime <N>h|<N>d|<N>m` (or `LEAF_LIFETIME`); the 365-day default is gone, and a
  call without one exits 2 and writes nothing. It also gains `renew` and `revoke`. The
  chart's `bootstrap.sh` likewise has no `LEAF_DAYS` default for a run that mints.
  Scripts that call either need the lifetime added (ADR 0088).
- **Building from source needs Rust 1.96** (was 1.88): the WebAssembly runtime requires
  it. `mqttd-operator` still builds with 1.89. Release binaries are unaffected.
- **The binary is larger.** A static, stripped `aarch64-unknown-linux-musl` build of this
  tree is 24.3 MB, and 16.9 MB when built with `--no-default-features`, which leaves the
  WebAssembly runtime and the jq module out (7.4 MB). The 1.1.0 release binary for that
  target was 14.7 MB. Those two builds were made on a development machine. Built by the
  release recipe (`scripts/release/build-repro.sh`), `x86_64-unknown-linux-musl` is
  33.5 MB, where the 1.1.0 release binary was 18.7 MB. The sizes of this release's own
  binaries are in the asset list below.

### If you switch `jq` on, or declare a module

`jq` is off unless `rules.jq = true` (`MQTTD_RULES_JQ=1`); a rules file that calls it
then does not load. The setting is read at startup, on every node. A module needs no
switch: declaring a `[functions.<name>]` table is the switch.

Compiled WebAssembly needs memory the process may map executable. **Under the shipped
systemd unit that is forbidden**, so on every node that will run such rules add a
drop-in (`sudo systemctl edit mqttd`) and restart:

```ini
[Service]
MemoryDenyWriteExecute=false
```

The unit file itself is unchanged and stays hardened; do not edit it. The container
image and the Helm chart impose no such restriction and need no change. If you forget
the drop-in nothing crashes: a rules file that calls `jq` or declares a module fails to
load and says why. At a start that means the broker exits with that error; at a reload
the running rules stay. `mqttd --check-config` run under the unit's settings says which
host it is on. What you give up, and how to bound what `jq` and modules can cost, is in
`docs/HARDENING.md` (H-7.12 to H-7.15) and `deploy/systemd/README.md`.

## New configuration

The rule engine's keys are under `[rules]`; none is set by default, and without
`rules.file` there is no rule engine. The full text is in `docs/CONFIGURATION.md`.

| Key | Environment | Default | What it does |
|---|---|---|---|
| `rules.file` | `MQTTD_RULES_FILE` | unset | The rules file. Reloaded on `SIGHUP` |
| `rules.sys_interval_secs` | `MQTTD_RULES_SYS_INTERVAL` | `0` (off) | Seconds between rule statistics on `$SYS` |
| `rules.trace` | `MQTTD_RULES_TRACE` | `false` | The rule trace on `$SYS`. It copies payloads: read HARDENING H-7.9 first |
| `rules.trace_rate` | `MQTTD_RULES_TRACE_RATE` | `20` | Trace records per rule per second |
| `rules.admin_writers` | `MQTTD_RULES_ADMIN_WRITERS` | none | Admin certificate subjects that may write the rules file through the admin API |
| `rules.jq` | `MQTTD_RULES_JQ` | `false` | Switches `jq/2` and `jq/3` on. Read at startup |
| `rules.jq_default_timeout_ms` | `MQTTD_RULES_JQ_DEFAULT_TIMEOUT_MS` | `10000` | `jq/2`'s timeout, as in EMQX. Read at startup |
| `rules.jq_env` | `MQTTD_RULES_JQ_ENV` | none | Environment variables a jq program may read. Read at startup |
| `rules.functions_env` | `MQTTD_RULES_FUNCTIONS_ENV` | none | Environment variables a module may be shown. Read at startup |
| `rules.function_max_ms` | `MQTTD_RULES_FUNCTION_MAX_MS` | `10000` | No jq or module call runs longer, whatever a rule or a payload asks for. Read at startup |
| `rules.state_max_bytes` | `MQTTD_RULES_STATE_MAX_BYTES` | 256 MiB | Ceiling for all rule state on a node; `0` switches state off. Read at startup |
| `rules.state_expiry_per_sec` | `MQTTD_RULES_STATE_EXPIRY_PER_SEC` | `1000` | Pace of `$events/state/expired`. Read at startup |

Under `[tls]` (ADR 0088), both read at startup:

| Key | Environment | Default | What it does |
|---|---|---|---|
| `tls.expiry_warn_permille` | `MQTTD_TLS_EXPIRY_WARN_PERMILLE` | `667` | How much of its lifetime a certificate, CA or revocation list may spend before the broker warns (two thirds) |
| `tls.end_sessions_at_cert_expiry` | `MQTTD_TLS_END_SESSIONS_AT_CERT_EXPIRY` | `false` | End a client session the second its certificate passes `notAfter` |

The chart gains `secrets.peerTls.certManager` and the operator
`spec.secrets.peerTlsCertManager` (`duration` and `renewBefore` required), for peer
certificates issued per pod by cert-manager's csi-driver.

Also new on the admin API: the rules routes (`/admin/v1/rules…`) and the rule state
routes (`/admin/v1/rules/state…`), and the audit kinds `rules.write` and `state.delete`
(`docs/AUDIT-SCHEMA.md`; new kinds are additive, as promised).

## Where mqttd differs from EMQX

Listed in full in `docs/RULES.md`, "Differences from EMQX". The ones most likely to
matter when porting rules:

- Actions are `republish` and `console`. A rule that names a data sink does not load.
- Limits EMQX does not have: on rule state, on `jq` and module calls, on regular
  expressions, on what one message's functions may build, and on the size of an integer.
- `jq` is off by default, and `$ENV` in jq is empty unless the operator lists variables
  (`rules.jq_env`).
- A chain of rules republishing into each other stops 32 republishes deep.
- `proc_dict_*` is one dictionary per connection, bounded, and empty for a Will and for
  events about a session that has no connection.
- Conditions EMQX fails on every message and mqttd evaluates (`x NOT IN (…)`, a bare
  value as a condition). A rule relying on them does not port back to EMQX.
- The `kv_*` functions, `[state.<name>]`, `$events/state/expired` and
  `[functions.<name>]` are mqttd's own; EMQX has none of them.

## Known limits of this release

- **With durable sessions (the default), a node that holds a member dead and cannot
  reach it for eight seconds acknowledges QoS 1 and QoS 2 publishes for that member's
  subscribers and does not deliver them** (#973) — a partition between the two that
  outlasts the verdict by that long. Until then, and for as long as the link between
  them is merely down, such a publish is held: its publisher waits, and it is delivered
  when the link is back. A verdict that is wrong while the network works costs half a
  second, because the node keeps dialing a member it holds dead;
  `mqttd_publish_held_for_unreachable` counts what is being held. Past the eight
  seconds the publisher gets a normal acknowledgement, and the publish is counted in
  `mqttd_publish_resolved_undeliverable_total{reason="hold-expired"}`. With
  `MQTTD_DURABLE=0` there is no such bound: the publish is held until membership
  confirms the member gone — its tombstone pruned with the parting greeting
  unanswered, 30 seconds after the verdict, or a new process under its node id — and
  then acknowledged and counted (`reason="peer-gone"`, or `"no-shared-member"` for a
  `$share` group that had members only there). A persistent session on such a node is
  treated as gone with it: a node that comes back with its disk does not have the
  messages published in between. One narrower case
  remains inside them, with durable sessions (the default; not with `MQTTD_DURABLE=0`):
  a subscriber on a member wrongly held dead loses a publish if any other subscription
  matching its topic newly appears in the cluster before the link is back. What was
  held is delivered in publish order when the link returns, and a `$share` message is
  acknowledged only when a member whose session is still there took it — except that a
  v1.1.0 node, during a rolling upgrade, still answers for a consumer that disconnected
  in the milliseconds before the message reached it. In the other direction of the roll,
  a 1.1.0 node whose `$share` message was refused by a 1.2.0 node because the consumer
  had gone gives it to another member; if the group has none it refuses the publisher as
  it would in a brownout (`0x97` for MQTT 5, a closed connection for 3.1.1) and logs
  `publish refused … refusal=brownout` at WARN, with no brownout and no counter moving. A healthy formation produces no
  such verdict, and neither does a member that is out of reach for just under two
  seconds (see "A member that is silent for a moment" below). A wrong verdict can
  still follow an outage of one member of about two seconds or more that then ends
  (in simulation rare at 2.5 s, up to one run in four at 3 s); sustained
  packet loss on the cluster network (in simulation, one datagram in ten lost: one run
  in three at 30 nodes, one in sixteen at 14, none at 10 or fewer, within 75 s); and,
  during the rolling upgrade, an outage of any length from half a second while nodes
  are still on 1.1.0 (#975). The
  rest of the fix — with durable sessions, a held publish resolved only by evidence or
  by confirmation that the member is gone (ADR 0087 D8, 0087-T5) — is designed and is
  not in this release.
- **A minority side of a partition can acknowledge a QoS 1 publish to a durable
  session and lose it at the heal** (#1030). A node that holds a session group's lease
  keeps writing under it while it is cut off with a minority of the cluster: with a
  replication factor below the cluster size, the replicas it reaches can make the write
  durable there, and the majority side reassigns the group meanwhile. When the
  partition heals, the deposed holder's writes are superseded. It needs a partition
  that isolates the lease holder with enough of the group's replicas; a node that is
  simply down, or a lost link between two nodes, does not cause it. A fix (a bounded
  lease on durable writes, or quorums from the durable roster) is being designed.
- **A node whose session scans never complete holds some QoS 1 acknowledgements
  indefinitely** (#1049). If a node cannot read one of the durable sessions it owns
  (it reports `NoQuorum` for it, again and again), each scan of its sessions stays
  incomplete, and it holds the PUBACK of every publish that matches no session it
  knows, until a scan completes. `/readyz` stays ready. Every incomplete scan is
  logged, naming the sessions it could not read and why (`session scan incomplete`
  at WARN, on the first and then every tenth), and `session scan complete again` marks
  the end. Seen once in the field, under heavy churn on a two-replica cluster; not
  reproduced yet. A restart does not clear it. Mitigation: send QoS 1 publishers to
  the other nodes, which acknowledge normally and still deliver to subscribers on the
  stuck one.
- **QoS 1 messages re-sent after a node dies, or after a live connection is moved to
  its session's owner, arrive as new messages** (#1058): `DUP` is 0 and the packet id
  is new, because the node that re-sends them never sent them itself. A client that
  deduplicates on `DUP` sees them as new. Nothing is lost; at-least-once allows the
  copy. QoS 2 is not affected: its packet id and phase are durable (ADR 0057). A
  durable record of what was sent, so these copies carry `DUP`, is planned.
- **During a session's ownership move, a publish the old owner refuses may already
  have reached the new owner's live subscribers** (#1054). The publisher retries (on
  MQTT 3.1.1 the refusal is a closed connection), and each retry reaches those
  subscribers again until the old owner lets the session go, usually within a second.
  Nothing is lost.
- **Rule state is experimental, because it is in memory.** A node that restarts comes
  back empty and, for `eventual` namespaces, is filled again by the other members; when
  every node stops, it is gone. No backup carries it. Every rules file that uses state
  loads with a warning that says so, at startup, on reload, in `--check-rules` and in the
  admin API. It stays experimental until it is durable (a snapshot to disk, then
  `strong` consistency): until then the state functions, `[state.<name>]` and the
  state admin routes may change in a minor release. The rest of the rule engine is not
  experimental.
- **`strong` consistency is not built**; a namespace that asks for it is refused at load.
  In an `eventual` namespace a message can be counted once per node inside the
  replication lag, and nodes hold differing copies while a namespace is at its bounds.
- **Concurrent long `jq` or module calls are bounded in time each**
  (`rules.function_max_ms`), **not in number.** Set a memory limit on the process.
- **Deleting state through the admin API is one key per request.** Purging a namespace
  and changing the expiry of stored keys are planned.
- With `jq` on or a module declared, a compiler (wasmtime's Cranelift) is in the
  broker's trust base, and three C libraries (PCRE2, zlib, liblz4) run in-process for the
  rule functions that need them. `docs/THREAT-MODEL.md` has the accepted risks.

## Cost

Microbenchmarks on one Apple M1 Pro, 2026-10-12, not idle (load average 9 to 21), the
fastest of three rounds. Not a cluster benchmark.

- Rules that use neither `jq` nor state cost what they did before those were added (the
  commit before both against this tree, alternating rounds): a publish no rule selects
  86.4 and 85.9 ns; a `WHERE` that rejects 751 and 756 ns; a `WHERE` that passes with
  one republish 1,399 and 1,401 ns; `SELECT *` with a JSON republish 3,749 and 3,715 ns;
  a `FOREACH` over ten elements 6,342 and 6,435 ns. Between 0.9% faster and 1.5% slower.
- A publish through one rule: 1.40 µs without state, 1.76 µs with a `kv_incr`, 2.23 µs
  with an idempotency key, 1.84 µs with a `kv_incr` in an `eventual` namespace.
- Between two nodes on loopback, a write was readable on the other node 1.3 ms later,
  and a peer caught up on 100,000 keys in 89 ms.

## Also in this release

- **Wills follow MQTT 5 more closely** (#1048). A Will now carries its Message Expiry
  Interval to its subscribers, as the publish it becomes. A client that reconnects and
  takes its session over within the Will Delay no longer has its old Will published.
  And a client that connects with Clean Start and a non-zero Session Expiry Interval
  keeps the new session when it has no subscriptions yet, as the specification
  requires; it was discarded at disconnect. A rules-live scenario suite checks every
  Will case against MQTT 3.1.1 and 5, in the demo and in CI (#1036).
- **An outbound Topic Alias is taken back when its PUBLISH is dropped as too large**
  (#1047). The alias was set up for a message that never went out, and the next PUBLISH
  on that topic named an alias the client had never seen.
- **Readiness waits for the first lease** (#1050): a freshly founded node reports
  ready only once the lease group has minted a lease, so the first retained writes and
  persistent sessions after `/readyz` turns green no longer fail.
- **A publish forwarded to a node part-way through a lease takeover reaches the session
  that moved there** (#1053). A node taking over a group answered a forward for its
  other subscribers at once, so the publisher was acknowledged while the session that
  had just moved there was still being loaded, and that session never got the message.
  The node now answers once its takeover scan has landed, and hands the publish to the
  sessions the scan brought. Only a node in a takeover holds the answer, and only until
  its next scan; no setting.
- **A resumed session is not sent messages it already acknowledged** (#1057). When an
  older QoS 2 message's release was held back (no quorum after a node failure), the
  QoS 1 messages acknowledged after it stayed queued and were re-sent as new messages
  when the client resumed on the same node.
- **The independent history checker judges more of MQTT** (#1039): QoS 2 exactly
  once, no protocol error seen by a client, Wills published when owed and only then,
  and Session Present across clean start and session expiry.
- **Certificate lifetimes are visible** (ADR 0088): `mqttd_tls_expiry_seconds{role}`
  and `mqttd_tls_lifetime_spent_ratio{role}` for every certificate, CA bundle and
  revocation list a node has loaded, a WARN once `tls.expiry_warn_permille` of a
  lifetime is spent and an ERROR once it has expired, and an alert in the chart's
  alert rules. See Upgrading for links ending at expiry.
- **Clusters above about ten nodes form without a storm of false suspicions, and a
  member falsely declared dead comes back** (#971). With signed gossip, two nodes that
  were not each other's seed used to drop each other's datagrams until one happened to
  send the other its full certificate; at 12 and 14 nodes that meant dozens of false
  `SUSPECT` and several false `DEAD` per broker during formation, minutes to settle,
  and at worst a pair in which one broker held the other out for good. A node now shows
  its certificate on the first datagram to each peer and again when a peer restarts,
  asks for a certificate it lacks, and greets a member once as it forgets it. In
  simulation a 14-node formation settles in 8 s (12 s at worst) with no false
  suspicion, where 1.1.0 took 215 s and did not settle within five minutes in a quarter
  of the runs; a member falsely declared dead is back within 30 s. The gossip wire
  format is unchanged and a 1.1.0 node interoperates, but nodes still on 1.1.0 keep the
  old behaviour among themselves until they are upgraded. New counter:
  `mqttd_gossip_cert_requests_total`, the certificate requests a node has sent
  (ADR 0022 and ADR 0016, amendments of 2026-10-12).
- **A member that is silent for a moment is no longer declared dead** (#975, #999).
  A node that has suspected a member for the full suspicion window (4 s, 1.5 s once
  three nodes suspect it) used to declare it dead there and then, and the refutation of
  a member that was already back often lost that race: in simulation a member cut off
  for 1.5 s ended up declared dead by some node in half the runs at 14 nodes and in
  three quarters at 30, each time for 30 s. A node now asks the suspect once more,
  directly, and declares it dead only if that goes unanswered too. A member cut off
  for up to 2 s is declared dead in no run at any size from 3 to 30 nodes, and one of
  twelve real brokers stopped for 2 s was declared dead in none of 68 stops. The
  price: a broker that really died is held dead by every other node about 0.3 s later
  (5.6 s in the median at 14 nodes, 8.3 s at worst; 0.6 s later at worst across sizes).
  Not a setting, and no change to the gossip wire format: a 1.1.0 node answers the
  question like any other probe. It does not ask it, so during the rolling upgrade the
  benefit arrives node by node, and a verdict a 1.1.0 node reaches is still adopted by
  the others (ADR 0016, amendment of 2026-10-13).
  The two seconds are arithmetic on the release's timings, and stated exactly they are
  two seconds less twice the network's latency: nobody suspects a silent member
  sooner than 0.5 s into its silence (two 0.25 s timeouts), nor asks it the last time
  sooner than 1.5 s after that, so the question is put once the silence is over. (The
  simulated figures above reach a full 2 s, and 2.1 s, because the simulation's nodes
  act on a timeout exactly on a 0.1 s grid; a broker's do not.) And it holds when the
  node asking is the one in trouble (#1002): a broker that was not scheduled for a
  while — every worker busy, a paused VM — reads what arrived while it was away before
  it concludes anything. Its own lateness does not make it slower to see a real death
  by more than the lateness itself. New metrics:
  `mqttd_swim_last_probes_total{outcome}` (`sent`, `spared`: the member answered,
  `silent`: it was declared dead); `mqttd_swim_stalls_total` and
  `mqttd_swim_stalled_milliseconds_total`, how often and for how long a node found its
  own membership task had not run; `mqttd_swim_awareness`, the node's local-health
  score (0 when healthy).
- A reload sent very early in startup no longer ends the broker: `SIGHUP` is registered
  at startup, with the stop signals (#954).
- Durable-path instrumentation: sampled transit stages on the peer link, and its
  `write_wait` counter.
- Bench rig: NIC counters, the peer bus over the public network, lane E ladder fixes.
- Eleven dependency update pull requests.
