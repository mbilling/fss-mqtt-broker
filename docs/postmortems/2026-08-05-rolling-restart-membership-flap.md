# Post-mortem: a rolling restart left a node NotReady forever — a `Dead` claim that never drained

**Date:** 2026-08-05 · **Environment:** ADR 0055 T7 operator e2e on kind (macOS/arm64, 3-node StatefulSet, `durable.enabled=true`, `lease_voters=3`) · **Status:** root cause confirmed and FIXED (membership claims carry a process generation, [ADR 0016 amendment](../adr/0016-swim-membership-stability.md))

> Related: [ADR 0016](../adr/0016-swim-membership-stability.md) (the tombstone rule this
> corrects), [ADR 0055](../adr/0055-kubernetes-operator.md) (the e2e that found it),
> [ADR 0047](../adr/0047-kubernetes-deployment.md) (the chart's roll).
> Issue: [#92](https://github.com/mbilling/fss-mqtt-broker/issues/92).

## Summary

After a StatefulSet **rolling restart**, one pod flapped `alive → dead → alive → dead`
in its peers' membership views every ~30 seconds, indefinitely. Every `Dead` transition
dropped the peer link and the node's routing state; with no link, the durable lease group
could not register that node, so it campaigned forever without electing; readiness
requires `lease_group_ready`, so the pod stayed **NotReady permanently**.

The cluster kept serving — the other two nodes held quorum — so nothing alerted. A
three-node fleet silently ran on two, with no quorum margin, after the most routine
operation a clustered broker has. It never healed.

## What actually happened

Three facts compose into a stable loop:

1. **A restarted process re-enters at the bottom of the incarnation range.** Incarnation
   numbers are per-process and not persisted, so a returning node starts where a brand
   new one does. A Kubernetes pod keeps its node id across restarts.
2. **`Dead` outranks `Alive` at equal incarnation** (`state.precedence()`), so a `Dead`
   claim about the node's *previous life* beats the new process's `Alive`.
3. **A claim never drains, because applying one re-gossips it.** `apply_update` ends in
   `enqueue_gossip(u)` — every node that accepts a claim re-arms its own dissemination of
   it. So the stale `Dead` kept circulating as long as anything kept re-accepting it.

The tombstone rule (ADR 0016 §1) then supplied the metronome. A `Dead` member is
tombstoned for `dead_ttl_ms` (**30 s** — exactly the observed flap period), during which
nothing can revive it, and is pruned afterwards. So: prune → the live node's `Alive`
re-inserts it → the still-circulating `Dead` re-kills it → tombstone for another 30 s →
prune → … forever.

ADR 0016 §1 had anticipated the restart case and dismissed it in one sentence: *"A node
that genuinely restarts rejoins after the tombstone is pruned … it does not need to
out-race stale gossip."* It does have to out-race it, and it always loses, because the
gossip it would have to outrun is regenerated by the very act of losing.

Evidence from the live cluster — the roll ordered `e2e-2`, `e2e-1`, `e2e-0`, and `e2e-2`
(restarted **first**) is the one that ended up isolated:

```
19:09:09.006  membership: peer alive; establishing link peer=e2e-2 addr=e2e-2...:7001
19:09:09.009  peer link established local=e2e-0 peer=e2e-2
19:09:09.054  membership: peer dead; dropping link peer=e2e-2      <-- 45 ms later
...
19:10:39.515  membership: peer alive; establishing link peer=e2e-2 ...
19:10:39.571  membership: peer dead; dropping link peer=e2e-2      <-- 56 ms later
```

and on `e2e-2`, terms climbing without end, both peers never granting:

```
elect, new candidate: {T113-N5571862232847142412 ... progress:{...: false, ...: false}}
ERROR openraft: while requesting vote error=Unreachable node: raft node ... unreachable
```

`e2e-2` is structurally the most exposed node: **only the smaller node id dials**, so it
is purely passive and cannot repair its own links. `Unreachable node` never meant a bad
address — the raft layer holds channels, not addresses, so it means only "no live peer
link is registered".

## Why no test caught it

- `scripts/k8s/kind-smoke.sh` **does** roll the cluster and was green. `kubectl rollout
  status` returns the instant every pod is Ready — and every pod *is* Ready then. The
  flap needs ~30 s to appear. The smoke read its retained value immediately and deleted
  the cluster. **Nothing in CI ever looked at a rolled cluster a minute later.**
- The SWIM unit tests covered the tombstone rule thoroughly, including
  `a_dead_member_is_not_revived_by_stale_higher_incarnation_gossip` and
  `a_tombstone_is_pruned_after_its_ttl_and_the_id_can_rejoin`. Both assert the *fence*
  works. Neither modelled a node **rejoining while its own death notice is still in
  circulation** — the composition, not the parts, was the bug.
- The deterministic SWIM simulation never restarts a node under an id it already used —
  so the one harness built to explore membership edge cases could not reach this one.

## The fix

Membership claims now carry the subject's **process generation** — a monotonic per-start
token (wall-clock ms at start; the state machine takes it as a parameter and stays
clock-free). Ordering is generation, then incarnation, then precedence:

- a claim at a **lower** generation is about a previous life: discarded outright;
- a claim at a **higher** generation supersedes everything held about the older life,
  **including its tombstone** — a restart is not a resurrection;
- at the **same** generation, every ADR 0016 §1 rule applies unchanged, so a dead
  process's own in-flight refutation is still fenced out exactly as before.

Two adjacent defects found in the same investigation, each of which could turn a
transient teardown into a permanent one, were fixed with it: an address change that did
not alter state raised no membership event (a dialer kept its spawn-time address for the
life of the process), and a peer first seen through relayed gossip *without* a routing
address was dropped permanently instead of being picked up when the address arrived.

## What now guards it

- `a_restarted_node_is_not_re_killed_by_its_previous_lifes_dead_claim` — the loop itself,
  reproduced in-process and deterministic.
- `a_tombstone_fences_the_dead_life_but_not_a_new_one` — the fix does not weaken ADR 0016.
- `claims_about_a_previous_life_are_ignored_whatever_they_say` — inert in every direction.
- `a_changed_routing_address_is_surfaced_even_when_the_state_is_unchanged`.
- `a_restarted_node_rejoins_and_stays_alive` (deterministic sim) — closes the harness
  gap that no scenario ever restarted a node under a used id. Stated plainly: this one
  does *not* fail against the pre-fix build. Five sim nodes on a reliable network drain
  their gossip before the tombstone prunes, so they rejoin cleanly; reproducing the loop
  needs a `Dead` claim still in flight at prune time, which production feeds through
  `Join` → `gossip_full_state` re-broadcasting a `Dead` the responder still holds. The
  scenario earns its place as an invariant, not as this bug's regression test.
- **kind smoke: a post-roll stability gate.** After the roll it now waits 90 s and asserts
  every pod is *still* Ready. This is the check whose absence let a permanent
  availability defect sit behind a green nightly.
- The ADR 0055 T7 operator e2e's scale cycle — withheld while this bug stood — is
  asserted again.

## Lesson

A test that asserts "the operation completed" is not asserting "the system is healthy".
`rollout status` returning is the *weakest* moment to measure a distributed system: it is
defined as the instant the last pod became Ready, which is precisely before any
membership consequence of the restart has had time to land. Every convergence assertion
in this repo should now be read with the question *how long after the disturbance does
this measure?* — and if the answer is "immediately", it is measuring the disturbance, not
the recovery.
